# 我为什么要做这个

## 一、先说明一下路测内容的来源

首先做一个叠甲，路测的内容是我利用AI根据我的项目代码，项目构建报告，芯片选取分析等进行整合得到的

## 二、为什么要增加板卡测评这个环节

至于我为什么要做一个测评的环节，目前实验室大家在学习的过程中目前板卡的接触比较少，可以说局限在了STM32\ESP32\ARDUINO\MSP这类的板卡上面，甚至目前你们接触到的这些大类板卡也都是基础的型号，

只是使用这些板卡的学习很难让你们能在今后的面试，就业这类的环境中拿到优势，

举一个简单的例子，现在的面试如果你还在用STM32F103来完成项目，那么你的项目很难有什么说服力了，双核不了解，芯片通信不了解，驱动开发还停留在调用整个地步，那么你基本上没有什么优势了，

并且现在这个环境，MCU的市场也是越来越复杂，MCU的板卡也逐步开始利用更好的RTOS架构进行开发，也不再是以前的单核架构，

所以你们需要接触更多的板卡，了解更多的知识才能开拓自己的眼界。

## 三、先把 MCU、SoC 和计算板这几个概念分清楚

那么在往下聊之前，我觉得有几个概念需要先说明白，不然你们看到一块新的板卡，第一反应还是看它是不是 STM32，主频有多少，能不能跑一个屏幕，最后买回来做的事情还是一样的。

**MCU、SoC 和计算板，并不是完全平行的三种芯片。** MCU 是微控制器，SoC 说的是把多种系统功能集成在一颗芯片上的形态，很多 MCU 本身也属于 SoC。你们看到 ESP32 被叫作无线 SoC，并不意味着它就和跑 Linux 的应用处理器是一类使用方式。[乐鑫 ESP32-S3 产品说明][ref-esp32]

为了方便后面讨论，我这里把它们按学习和项目里常见的叫法分开说：

| 常见叫法 | 主要关注什么 | 你们接触时应该看什么 |
| --- | --- | --- |
| MCU 板卡 | 外设采集、实时控制、低功耗、设备连接，也可以承担界面和一定的本地计算 | 中断、定时器、ADC、DMA、内存、RTOS、通信与错误恢复 |
| 应用处理器 SoC 板卡 | 更复杂的操作系统、图形、多媒体、网络，以及一定规模的边缘计算 | Linux / Android、BSP、设备树、驱动、DDR、存储、图像接口和系统性能 |
| 计算板、核心板或计算模组 | 将处理器、内存等组成可用硬件，给具体产品提供计算能力 | 芯片能力之外，还要看接口引出、载板、电源、散热、系统支持和产品生命周期 |

这里的“应用处理器 SoC”主要指 i.MX、瑞芯微等跑复杂系统的平台；“计算板”则可能是树莓派单板机、配合载板使用的 Compute Module，也可能是 Jetson 这类边缘计算平台。板卡形态和芯片类型不是一回事，计算板里面同样要有处理器，某些 SoC 内部也同时放了应用核和实时核。[NXP i.MX 93][ref-imx93]、[Raspberry Pi 工业应用][ref-rpi]

另外，原文把 STM32、ESP32、ARDUINO、MSP 放在一起，是在说大家平时接触的开发平台。严格区分的话，Arduino 是开发板和软件生态，底下也可以采用不同厂商、不同架构的芯片。所以你们认识一块板卡的时候，最好继续往下看，搞清楚它用的具体芯片、核心和内存，而不是只记住外面那个名字。

## 四、如今的嵌入式板卡，已经有哪些变化

### 1. 同一个系列里面，能力的跨度也可能非常大

原文拿 F103 举例，想说的是大家需要往外看。F103 仍然可以用来学 C、寄存器、中断和外设，项目有没有说服力，最后还是要看你解决了什么问题，以及你能不能把过程讲清楚。换了一块性能更高的板卡，如果还是只做初始化、点灯和调用例程，项目深度也不会自动增加。

就算继续学 STM32，也有很多东西可以往下做。比如 STM32H747/757 使用 Cortex-M7 和 Cortex-M4 双核，你需要考虑任务怎么分配、共享数据怎么交换、外设由谁管理，而不只是把主频换了一个数字。[ST 双核 STM32H7 说明][ref-stm32h7]

再比如这次的 FRDM-MCXN947，它提供双 Cortex-M33，以及 NPU、PowerQuad 等资源。你们可以先把 GPIO、UART、屏幕和存储做好，再逐步接触双核通信和本地推理。板卡有这些资源，只能说明它给你提供了继续学习的入口，具体能运行什么模型、使用多少内存、能达到什么效果，还是要看算子支持、工具链和实际测试。[NXP FRDM 与边缘计算平台介绍][ref-mcx]

### 2. 开发越来越需要系统思维，但单核和裸机仍然有自己的位置

现在你们能接触到的项目，除了外设驱动，还可能同时有 RTOS、文件系统、网络协议栈、图形界面、升级和日志。功能一多，就需要考虑哪些事情放在中断，哪些事情交给线程，缓冲区归谁管理，某个模块卡住以后会不会拖住整个系统。

这也是我希望你们多接触板卡的一个原因。同样是“串口不通”，可能是线接反，也可能是时钟被其他模块改了；同样是“屏幕花了”，可能是通信时序，也可能是 DMA 长度、缓存或者刷新区域出了问题。只会调接口，遇到几个模块一起工作的情况就很容易没有思路。

不过项目的需求仍然有大有小。一个简单、低成本、低功耗的控制节点，完全可能继续使用单核 MCU 和裸机程序。多核、RTOS 和 Linux 都需要解决具体问题，你们需要学会判断什么时候值得引入它们，以及引入以后增加了什么成本。

### 3. 联网、本地计算和 AI 开始出现在更多层次的设备里

你们现在做一个语音设备、智能门锁或者交互终端，可能会碰到 Wi-Fi、蓝牙、本地音频处理和设备升级。往上做视觉识别和机器人，又会碰到摄像头、模型部署、GPU / NPU、内存带宽和散热。乐鑫有面向联网交互的 ESP32-S3 平台，NXP 有带机器学习加速的 i.MX 93，Jetson 则提供面向机器人和边缘 AI 的计算平台，这些产品对应的资源规模和工程路径并不一样。[ESP32-S3][ref-esp32]、[i.MX 93][ref-imx93]、[NVIDIA Jetson][ref-jetson]

这里还要分清楚模型到底在哪里跑。设备通过网络请求云端大模型，和设备自己完成本地推理，涉及的内存、算力和网络依赖是两回事。不能接上一个大模型接口，就说自己已经掌握了端侧模型部署；也不能只看到 TOPS，就认定整机的识别速度一定更快。

### 4. 开发板能跑通，距离做成产品还有一段路

学生项目往往先关心功能有没有出来，企业还要考虑断电、断网、升级失败、设备长时间运行，以及后续能不能继续供货和维护。计算板还会增加电源、散热、启动时间和系统镜像管理等问题。

所以你们看到核心板或者计算模组的时候，也应该顺便了解载板的作用。模组帮你集成了一部分复杂硬件，具体产品仍然要把接口、电源、外设和结构组织起来。开发套件适合验证方案，量产硬件的选型和验证还需要单独完成。[Raspberry Pi 工业平台][ref-rpi]、[Jetson 开发套件与模组说明][ref-jetson-faq]

## 五、MCU、SoC、计算板在各个行业里究竟做什么

下面我按典型工作内容来拆，帮助你们把板卡和真实产品联系起来。具体公司会根据成本、性能、功耗和已有方案选型，同一个行业也不会只用某一种芯片。表里的职责是工程归纳，列出的厂商资料用于核对相应平台和应用方向，并不代表所有企业都采用相同架构。

| 行业 | MCU 常承担的工作 | SoC、计算板常承担的工作 | 可以顺着补充的知识 |
| --- | --- | --- | --- |
| 汽车电子 | 车身控制、执行器、传感器接口、部分电池管理与区域控制功能 | 座舱交互、车载网络处理，以及需要更大规模计算的感知等功能 | CAN / CAN FD、LIN、车载以太网、诊断、AUTOSAR、启动与升级 |
| 工业自动化 | 电机和执行机构控制、周期采样、实时 I/O、设备保护 | 工业网关、操作界面、数据汇聚、视觉检测和上层调度 | ADC 与 PWM 配合、实时性、工业通信、Linux 驱动、可靠性 |
| 机器人、无人机 | 电机控制、编码器采集、底层状态机和及时保护 | 图像处理、定位导航、路径规划、模型推理和人机交互 | 闭环控制、时间戳、跨板通信、ROS 2、传感器与驱动 |
| 智能家居、家电 | 传感器、按键、电机、温控和低功耗联网节点 | 带屏中控、语音与视频处理、复杂设备管理 | 无线协议、功耗、设备配网、升级、图形界面 |
| 医疗与健康设备 | 低功耗信号采集、传感器连接、便携设备控制 | 复杂界面、数据管理，以及按设备需求配置的图像或信号计算 | 采样质量、功耗、数据完整性、异常状态与验证记录 |
| 新能源与电力电子 | 电源变换控制、电流电压采样、保护、部分电池管理功能 | 能源管理界面、网关、运行数据处理与远程运维 | ADC / PWM 同步、控制算法、隔离、通信、故障保护 |
| 安防、机器视觉 | 辅助控制、触发、状态采集与电源管理 | 摄像头接入、图像处理、编解码、识别和多路数据处理 | 摄像头驱动、ISP、DMA、视频链路、模型性能分析 |
| 物流、零售与农业设备 | 传感器节点、执行机构、现场控制和状态采集 | 机器人调度、识别终端、边缘网关、巡检和数据分析 | 有线 / 无线联网、控制与计算协同、离线运行、设备维护 |

平台与应用方向可以对应查看：[NXP 汽车 S32K3][ref-s32k3]、[ST 电机控制][ref-motor]、[TI 数字电源][ref-power]、[Nordic 可穿戴应用][ref-wearables]、[瑞芯微工业与视觉案例][ref-rockchip]、[NVIDIA 边缘计算应用][ref-jetson-industries]。上面是按产品职责划分的学习入口，医疗、汽车等产品实际采用的器件与软件还需要满足各自的产品要求，不能用一个学习板上的演示代替产品验证。

### 1. 汽车电子：车里面也有很多不同层次的开发

很多同学一提汽车就想到智能驾驶，实际上车窗、门锁、灯光、空调、车身网络和电池相关功能，也都有对应的控制任务。NXP 的 S32K3 就面向车身、车辆控制、区域控制和电气化等应用，MCU 在这些地方需要兼顾外设、实时响应和可靠运行。[NXP S32K3][ref-s32k3]

那么你们如果想往汽车底层软件方向走，学习的重点就不能只有“我能发一个 CAN 报文”。你还要继续理解报文是怎么配置和路由的，诊断怎么做，超时和 Bus-Off 怎么处理，软件怎么升级，出现问题后怎么留下能分析的记录。

如果往复杂界面或者感知计算方向走，关注点又会增加操作系统、图形和视频链路、模型运行以及计算资源分配。它们都属于广义的嵌入式相关工作，但是每天面对的问题和面试需要准备的东西会有明显区别。

### 2. 工业与新能源：很多时候，稳定地按时完成比多跑一个功能更关键

举一个简单的例子，你做一个电机项目，显示转速和让电机转起来是一个阶段，按固定周期采样、计算、更新 PWM，在负载变化时保持控制，并在异常时及时停下来，又是另外一个阶段。ST 的电机控制生态和 TI 的数字电源方案，都体现了 MCU 在这类实时控制中的作用。[ST 电机控制][ref-motor]、[TI 数字电源][ref-power]

到了上层，可能还需要一个 Linux 网关或者计算板，负责界面、数据汇总、设备联网和运维。同一个系统里，控制部分和管理部分可以由不同处理器分工；在一些平台上，也会利用不同核心承担不同职责。你们需要关心的是边界划在哪里，数据多久更新一次，上层失去响应的时候，底层应该怎么处理。

新能源也不能只理解成“用单片机采几个电压”。电源变换里的采样和控制周期、保护触发，以及设备运行状态，都需要按实际负载和控制目标设计。板卡主频只是其中一项，模拟外设、定时器、接口和开发生态也会影响方案。

### 3. 机器人与视觉：把控制链路和计算链路一起看

你们可以把一台机器人想成几条同时运行的链路。下面一层采集编码器、执行电机命令，上面一层接收相机和其他传感器数据，完成定位、识别和规划，中间通过约定好的协议交换状态和指令。Jetson 等平台提供的是机器人和边缘 AI 的计算入口，真正做项目仍然要把传感器、底层控制和异常处理连接起来。[NVIDIA Jetson][ref-jetson]

所以你们做 ROS 项目时，除了看节点有没有启动，也要追一下数据是从哪里来的。相机驱动有没有稳定输出，时间戳能不能对应，数据积压以后延迟多大，计算板发来的命令已经过期了，控制侧还要不要继续执行，这些都是可以深入做的事情。

安防和机器视觉也类似。摄像头出图、图像预处理、推理、结果输出，每一个阶段都会占用时间和内存。瑞芯微的工业与视觉方案里可以看到网关和视频分析这类应用，但你们做自己的项目，还是要测完整链路的吞吐和延迟，不能只拿单次模型推理时间代表整个设备的表现。[瑞芯微应用案例][ref-rockchip]

### 4. 物联网、可穿戴和便携设备：有些项目需要精打细算地用电

如果设备长期靠电池运行，或者体积比较小，追求高主频和更多线程可能很快就遇到功耗问题。Nordic 的可穿戴应用就包括手表、运动传感器和智能戒指等方向，强调低功耗连接与本地处理。[Nordic 可穿戴应用][ref-wearables]

这类项目里，你们可以继续研究什么时候采样、什么时候通信、什么时候休眠，异常断连后怎么恢复，以及日志本身会消耗多少电。智能家居的联网节点也有类似问题，只是供电方式、交互要求和通信环境不同。

做出一个能上传数据的设备，是功能闭环；再把稳定性、功耗和维护能力做出来，项目里能讲的内容就会丰富很多。

## 六、你们接下来应该怎么接触这些板卡

我希望的学习顺序，还是先把一条链路完整做出来，再逐渐把范围扩出去。板卡可以根据你们已经有的资源和想走的方向选，先把手上的平台利用起来。

**第一步，补齐一个外设的完整理解。** 从时钟、引脚、寄存器和驱动，一直看到中断、数据缓冲和上层接口。至少独立定位过一次问题，知道程序为什么没有按照预期工作。

**第二步，让几个模块同时工作。** 比如屏幕刷新、传感器采样、串口收发和文件日志放在同一个项目里，看看哪些地方需要队列，哪些数据需要锁，哪些操作不能在中断里做。开始记录内存、栈、错误和最长处理时间。

**第三步，按就业方向增加一条主线。** 想做 MCU 和控制，就往实时性、DMA、通信和控制算法深入；想做 Linux 驱动，就从系统启动、设备树、总线和设备驱动往下做；想做机器人或者端侧计算，就把模型、传感器和执行链路真正连起来，再去测性能。

**第四步，做一次迁移或者分工设计。** 可以把一个模块迁移到另一种 MCU，也可以让 MCU 和计算板通过串口、CAN 或以太网协作。迁移以后你会发现，有些代码可以复用，有些地方和芯片、操作系统、内存布局绑定得很深，这时候才能更具体地理解抽象和分层的价值。

你们最后写到简历里面，可以是“我解决了什么问题，用什么方法确认了原因，修改以后有什么结果”。如果能够拿出代码、构建报告、运行记录和波形，对项目的解释就有了依据，换不换板卡也就不是唯一的话题了。

## 七、所以我希望这个测评环节最后能留下什么

我希望一篇板卡测评能让你们知道，这块板卡的资源适合做什么，工具链和软件生态是怎样的，实际项目会遇到哪些问题，以及这些问题最后是怎么定位的。

能接触到更多的板卡当然有帮助，但是你们看完之后，最好还能带走一个可以继续验证的问题。比如双核之间怎么共享数据，屏幕和串口同时工作时怎么分配资源，文件系统写入会不会影响采样，模型运行期间设备的控制任务还能不能按时完成。

这个环节最后可以逐步积累成一组有代码、有过程、有结果的案例。你们需要做项目、准备面试或者选择方向的时候，能够顺着这些案例找到下一步要补的知识，这也是我想把这件事做下去的原因。

# 一个项目怎么写进简历，又怎么回答追问

很多同学做完项目以后，打开简历还是不知道应该写什么。写少了，感觉项目没有体现出来；写多了，又变成一串芯片、框架和通信协议的名字。等面试官继续问为什么这样设计、某个问题怎么解决时，才发现自己准备的内容和项目之间还没有联系起来。

这篇就用仓库里的 [FRDM-MCXN947 桌面机器人项目](../测评/FRDM%20MCXN947板卡路测.md)举例，聊一聊怎么把项目记录整理成简历，以及面试时怎样顺着自己的工作回答追问。

文中具体配置和运行数据来自这篇路测文章，是已有记录的整理，这次没有重新进行板上测试。下面的简历和口述示例用于说明表达方法，使用时只保留自己实际完成、能够解释和验证的部分；项目起止时间、团队分工等信息需要据实填写。

## 一、先把自己做过的事情弄清楚

在写简历之前，我建议你们先开一个文档，暂时不用考虑排版，把下面几件事写出来。

| 要回答的问题 | 可以整理的内容 |
| --- | --- |
| 这个项目准备解决什么问题 | 使用场景、需要完成的功能，以及主要资源约束 |
| 系统由哪些部分组成 | 主控、外设、通信节点、操作系统与业务模块 |
| 自己具体负责什么 | 实现、移植、集成、调试、测试，分别做到哪里 |
| 做过哪些取舍 | 为什么采用某个线程划分、缓冲方案或通信方式 |
| 遇到过什么问题 | 现象、复现条件、排查过程、根因与修改 |
| 最后拿什么证明结果 | 代码、提交记录、日志、波形、构建报告与测试记录 |

你们会发现，简历里最值得展开的内容，往往就藏在这些记录里。

比如“用了 Zephyr”和“用了消息队列”都比较宽泛。继续往下写：为什么界面回调不直接执行文件操作，工作线程从哪里接收请求，队列满了怎么办，这才逐渐接近你真正做过的设计。

如果一时整理不出来，可以先去翻自己的代码和调试记录。把缺少的测试补上，再决定要不要把这项能力写进简历。

## 二、把项目整体和个人贡献分开

团队项目可以写，跟着官方例程做移植可以写，复现开源项目也可以写。关键是说明原有基础是什么，以及你在这个基础上完成了什么。

| 实际情况 | 可以怎样说明 |
| --- | --- |
| 独立完成某个模块 | 写清模块职责、实现方案、异常处理与验证结果 |
| 和同学共同完成项目 | 先说明整体目标，再明确自己负责的模块和参与的协作 |
| 以官方例程为起点 | 说明复用了什么，增加或修改了哪些功能，解决了什么适配问题 |
| 复现开源项目 | 注明原项目，说明环境搭建、复现结果与自己的改动 |
| 只完成了其中一部分 | 写已经完成的范围，后续计划单独说明 |

例如，官方已经提供了显示例程，你完成了板级适配、刷新问题定位和业务集成，就可以据此写自己的工作。如果没有独立实现整套驱动，就把贡献具体到适配和修改的位置。

项目里使用了 AI，也可以按真实过程解释：它辅助了哪些代码或资料整理，哪些判断由你完成，生成的内容经过了什么检查，最后的结果怎么验证。对于一段写进简历的实现，你仍然需要知道它为什么这样工作。

## 三、技术栈要跟你做过的功能对应起来

有些同学怕项目显得简单，会把芯片支持的能力都往简历上写。这个地方需要特别注意，芯片具备某个外设或加速器，不代表项目已经使用了它。

以桌面机器人这份记录为例：

| 项目资料里的信息 | 能据此说明什么 | 还不能直接推出什么 |
| --- | --- | --- |
| MCXN947 是双核芯片，当前固件运行在 CPU0 | 在该平台完成单 CPU0 应用及相应资源规划 | 已经实现双核任务协作和核间通信 |
| 芯片具有 NPU | 了解平台提供的计算资源 | 已经完成模型转换、部署和性能测试 |
| UART 使用中断、环形缓冲和通信线程 | 实现了相应的字节接收与线程处理链路 | UART 已经采用 DMA 接收 |
| LCD 调试涉及 FlexIO/eDMA | 参与了该显示链路的数据传输适配 | 整个系统的所有数据都由 DMA 搬运 |
| PC 端有天气界面预览 | 复用界面源码进行布局与显示验证 | 板上已经实时获取到相同天气数据 |

这几组信息写清楚以后，面试时就更容易确定自己可以展开到哪一层。

对你们自己的项目也一样。用了一个摄像头，不自动等于完成了视觉算法；连通一个云端接口，也需要和本地模型推理分开说明。技术栈最好能在代码和数据流里找到对应的位置。

## 四、简历里具体应该怎么写

### 1. 先用一两句话交代项目

项目名称、时间和角色按实际情况填写。背景可以简洁说明目标、平台和系统关系：

> **桌面交互机器人｜起止时间与个人角色据实填写**
> 基于 FRDM-MCXN947 与 Zephyr，集成 LVGL 界面、待办管理、文件日志及设备通信，通过 UART 与 ESP32 节点交换数据，重点处理显示、存储和通信并发时的资源分配与调试问题。

这段的作用是让面试官先知道项目是什么。后面的条目再说明你负责的工作，不必把所有外设参数都塞进背景里。

### 2. 从真实工作中挑出几条重点

下面是一组基于路测记录的改写示例。只有当对应工作确实由你完成或承担了明确职责时，才适合保留相应表述。

- 完成 Zephyr 应用中的界面、桌面业务与通信模块集成，通过消息队列将命令执行和待办保存交给工作线程，使用模型快照缩短共享数据的持锁范围。
- 在 480×320、RGB565 显示配置下采用 15 KiB 局部绘制缓冲，并结合链接报告、线程栈水位与 LVGL 内存池统计分析资源占用。
- 定位 UI 初始化改变共享外设时钟导致的 UART 通信异常，将时钟配置前移至 UART 驱动初始化之前；原记录中的连续 30 次 PING/PONG 均返回，相关 UART 错误与坏帧计数增量为 0。

如果你主要负责串口模块，可以把第一条换成更贴近职责的内容：

> 实现 UART 中断接收、2,048 B 环形缓冲及通信线程解析链路，将字节接收与业务处理分开，并通过收发、错误和超时计数辅助定位通信异常。

条目不需要全部照搬。优先保留与你投递方向相关、自己能够讲透的几项，其余细节放在项目记录里备查。

### 3. 一条经历可以按这个顺序整理

**负责的部分 → 遇到的约束或问题 → 采用的方法 → 有依据的结果。**

例如，先写“串口不通”，接着整理是谁负责排查、检查了哪些状态、发现了什么时钟变化、修改后验证了什么，最后才压缩成简历中的一条经历。

没有性能测试的数据，也可以用明确的功能范围说明成果，例如“完成接收解析与超时处理，增加错误统计，验证指定测试序列的解析结果”。先把结果说准确，再考虑怎样表达得简洁。

## 五、数字怎么写，才经得起追问

数字可以帮助说明约束和结果，但要先弄清楚它的口径。

| 路测中的数据 | 可以怎样写 | 面试时需要解释的边界 |
| --- | --- | --- |
| 局部绘制缓冲 15,360 B | 使用 15 KiB 局部绘制缓冲 | 这是绘制缓冲，不是整个 UI 或整个固件的 RAM 占用 |
| 普通 RAM 链接占用 179,844 B | 该版本 CPU0 普通 RAM 链接占用约 54.88% | 分母是 320 KiB 分区，运行时各内存池的余量还要单独观察 |
| UI 栈记录中已用 4,020 B | 在对应测试记录中观察到该栈使用量 | 栈水位反映已覆盖路径，不是所有未来场景的理论上限 |
| 连续 30 次 PING/PONG 均返回 | 在该次回归中完成 30 次请求响应 | 不能直接扩大为长期、满负载或所有异常条件下零丢包 |

对于显示缓冲，还可以解释计算过程：

```text
480 × 320 × 2 B = 307,200 B，即 300 KiB 全屏像素缓冲
15,360 B = 15 KiB，是该全屏缓冲大小的 5%
```

这能说明选择局部缓冲的原因。如果要写“整机 RAM 降低了多少”或“帧率提高了多少”，还需要同等条件下的前后构建或测量记录。仅凭两个缓冲区大小，不能得出整机性能提升比例。

## 六、同一个项目，投不同方向时怎样取重点

可以调整叙述顺序，让面试官先看到和岗位相关的部分；经历本身仍然按真实完成的范围写。

| 准备的方向 | 这个项目里可以重点讲什么 | 需要准备的证据 |
| --- | --- | --- |
| MCU / RTOS 开发 | 线程与中断分工、缓冲区、队列、内存预算、异常处理 | 任务关系图、关键代码、栈水位与接收统计 |
| BSP / 驱动相关方向 | 时钟和引脚配置、初始化顺序、显示传输适配与寄存器排查 | 配置文件、修改位置、寄存器记录及验证过程 |
| 图形界面与交互 | 局部刷新、业务模型、后台任务与界面响应 | 界面演示、刷新配置、数据更新路径与资源记录 |
| Linux 驱动方向 | 可迁移的硬件排查与驱动适配经验 | 还应补充实际的 Linux 启动、设备树或驱动实践，Zephyr 经历不能直接写成 Linux 驱动经历 |
| 机器人 / 端侧计算方向 | 主控与节点分工、传感器数据、通信状态和故障处理 | 当前已实现的数据链路；ROS、导航或模型部署需要各自的实际实现与记录 |

桌面机器人这个名称，可以让别人理解产品形态。能否作为某个方向的技术经历，还要看项目里具体完成了哪些工作。

## 七、面试开始时，先把项目讲清楚

建议先准备一个能自然说出来的短版本。先说明需求和系统关系，再说自己的贡献，最后给面试官一个可以继续问的具体问题。

仍然假设相关工作确实是你负责的，可以这样组织：

> 这个项目是一个基于 N947 的桌面交互终端，CPU0 运行 Zephyr，承担界面、待办、文件日志和设备管理，另外通过 UART 和 ESP32 节点通信。我主要负责的是其中的界面与通信集成，以及相关资源和故障排查。
>
> 项目里需要让显示、文件操作和通信同时工作，所以我把一些慢操作交给工作线程，通过队列提交请求，同时分别记录线程栈和 UI 内存池的占用。
>
> 其中有一次 UART 初始化正常但收不到响应，最后发现后续的 UI 初始化改了共享时钟，使串口分频和实际时钟不匹配。调整初始化顺序后，按记录完成了 30 次 PING/PONG 回归。

如果你只负责串口，就把其他模块交代为项目背景，再集中讲自己的部分。面试官问到队友完成的代码，可以说明接口和已了解的设计，不必把全部实现都认领到自己名下。

## 八、把一个故障讲成完整的过程

面试官让你说“最难的问题”时，可以从一个自己有记录的问题讲起，按证据把过程串起来。

### 1. 现象是什么

UART 已初始化，接线与引脚配置经过检查，但是 N947 与 ESP32 之间的 PING 没有响应。

这里可以继续说明，排查时需要区分没有收到字节、收到无效数据，以及业务层没有回复。不同现象对应不同的检查方向。

### 2. 为什么没有停留在修改波特率参数

继续检查实际外设源时钟、分频寄存器和初始化顺序。资料记录中，UART 最初按 48 MHz 配置，后续 UI 相关初始化把共享时钟切换成了 12 MHz。

### 3. 怎样解释根因

保持原分频不变时，时钟由 48 MHz 变为 12 MHz，计算出的波特率也随之下降。路测中的计算为：

```text
48,000,000 / (32 × 13) ≈ 115,385 baud
12,000,000 / (32 × 13) ≈  28,846 baud
```

面试时要能把源时钟、分频字段和计算中的数值对应起来。引用这段计算前，也需要确认自己使用的是同一配置，不能拿别的芯片寄存器套进来。

### 4. 改了什么，为什么这样改

按原工程记录，将应用时钟配置前移至 `PRE_KERNEL_1` 的合适位置，使其先于 UART 驱动初始化，再由驱动根据最终时钟计算分频，并增加构建断言约束顺序。

这个修改希望把最终时钟配置与驱动初始化统一起来。实际复现时，需要核对所用版本的初始化级别、优先级和调用路径；同一个级别名称并不自动保证所有函数之间的先后关系。

### 5. 怎么确认修复有效

原文记录了连续 30 次 PING/PONG 返回，以及相关错误计数的增量。可以把它作为该轮回归的结果，同时说清楚测试版本和条件。

如果面试官问长时间运行、频繁重启或高负载下是否还存在问题，没有做过的部分就明确说明，并给出准备怎样补测的方案。计划中的验证与已经拿到的结果分开讲。

## 九、面试官可能沿着哪些地方继续问

下面是根据这个项目自行延伸的模拟追问，不作为任何企业的原题。回答方向也需要和你实际实现的代码对应。

| 追问 | 回答时可以沿着什么讲 | 可以准备什么材料 |
| --- | --- | --- |
| 为什么需要几个线程，优先级怎么定 | 各模块是否等待、是否耗时、对时延有什么要求，以及共享关系；拿出实际优先级配置 | 线程表、配置与运行记录 |
| 为什么不在触摸回调中直接保存文件 | 文件操作可能耗时，说明请求如何进入工作线程，以及结果怎样反馈给界面 | 回调到队列再到工作线程的调用路径 |
| 队列满了怎么办 | 先核对提交接口的返回值，再说明当前实现如何反馈、是否丢弃或重试 | 错误路径代码与满队列测试 |
| 为什么环形缓冲配置为 2,048 B | 给出速率、突发量和最长服务间隔的预算，再结合实际溢出记录；若尚无测量，说明这是待验证配置 | 接收速率、调度延迟和溢出统计 |
| 线程间共享数据怎么保护 | 写入者和读取者分别是谁，锁保护哪段操作，快照什么时候复制 | 模型接口和锁范围 |
| 为什么界面只用 15 KiB 绘制缓冲 | 计算全屏大小，结合 RAM 分区解释选择，再说明刷新方式及其代价 | 显示配置和 map 文件 |
| 当前的双核是怎么协作的 | 按当前记录说明只运行 CPU0 镜像，CPU1 相关工作不能当作已完成功能 | 构建目标和链接分区 |
| UART 有没有使用 DMA | 明确本项目记录中的 UART 中断接收链路，再区分 LCD 的 eDMA；可以讨论后续方案，但要标明尚未实现 | UART 和显示各自的数据路径 |
| 怎样判断栈够不够 | 说明工具、观测场景、已用与剩余，并交代覆盖盲区 | 栈水位记录、压力场景 |
| 文件保存过程中断电会怎样 | 解释实际写入流程、文件系统和 Flash 条件；是否做过掉电验证要单独回答 | 保存代码、存储配置和掉电测试记录 |
| 能不能证明系统长期稳定 | 给出实际时长、负载、计数和失败情况；当前 30 次通信回归只覆盖有限条件 | 对应运行记录，不补写未经测试的结论 |
| 如果再做一次准备改什么 | 从已有瓶颈提出一个改进，说明预期收益、代价和验证方法 | 问题列表与待做实验 |

### 一个缓冲区追问可以怎样继续准备

以 115200、8N1 为例，不考虑额外间隔时，每字节占 10 bit，连续输入速率约为 11,520 B/s。2,048 B 对应约 0.178 s 的理论填充时间。

这个估算可以帮助你判断，接收线程长时间得不到处理机会会有什么风险。实际还要考虑缓冲区是否预留空位、当前已有多少积压，以及最坏调度延迟。它不能单独证明 2,048 B 一定足够，仍需要结合代码和压力记录。

## 十、暂时回答不上来时，怎么继续交流

先说清楚自己已经确认的部分，再区分推测和后续计划，保持回答有依据。

例如，被问到队列满的情况，如果只看到过提交失败返回，却还没有主动构造过满队列场景，可以这样回答：

> 当前提交使用非阻塞方式，队列满时会返回失败，我会先确认上层对返回值的处理。满队列下界面怎样反馈、请求有没有遗漏，我还没有做完整的压力验证。后续准备让消费者处理变慢，连续提交请求，再检查失败计数、界面提示和数据一致性。

这种回答既说明当前理解，也给出了可以继续验证的办法。没有测试过的机制，不需要临场补出一个已经实现的结论。

## 十一、面试之前，可以准备一份自己的项目资料包

资料不必都发给面试官，先保证你自己能够查到，并且能用它核对简历。

- 一张系统关系图：主控、外设、线程和通信节点之间怎样交换数据。
- 一张个人职责表：自己完成、团队完成、沿用开源或官方实现的部分分别是什么。
- 一份环境记录：板卡、工具、SDK、固件版本及对应代码提交。
- 几段关键实现：一条数据路径、一个异常处理、一个实际修改的位置。
- 一份故障复盘：现象、证据、根因、修复和回归。
- 一份指标记录：每个数字的来源、单位、分母、测量条件与覆盖范围。

准备以后，找同学对着简历连续追问。每一条都问一下“为什么、在哪里实现、失败会怎样、拿什么验证”，再把暴露出来的空缺补到项目记录里。

实际笔试和面试中，工具使用按组织方规则执行。平时可以让 AI 帮你检查措辞、生成模拟追问和发现逻辑漏洞，再回到代码与资料验证，避免把生成的解释直接当成自己的实现经历。

## 十二、最后再检查一下简历里的项目

- 项目背景、时间和角色是否写清楚。
- 每条技术栈能否对应到具体功能或实现。
- 独立完成、团队协作、复现和移植是否分得清楚。
- 每个数字是否有来源，测试条件是否能解释。
- 至少能否完整说明一次问题定位与验证。
- 尚未实现或验证的部分，是否和已完成内容分开。

你们手里的项目可能规模还不大，但是只要有一段自己真正做过、能够讲清楚的过程，就可以继续往里面积累。把一次通信异常查明白，把一个缓冲区的边界验证清楚，把一段代码迁移到另一块板卡，都会慢慢变成能写进简历、也能经得起追问的经历。

## 一、C / C++ 基础

### Q001：一个 `.c` 文件如何变成可执行程序？

通常经历预处理、编译、汇编、链接四个阶段：

1. 预处理展开宏和头文件，处理条件编译，常见中间文件为 `.i`。
2. 编译进行语法、语义分析及优化，生成汇编代码 `.s`。
3. 汇编生成可重定位目标文件 `.o`，其中包含机器码、符号和重定位信息。
4. 链接合并目标文件和库，解析符号并按链接脚本安排段，生成 ELF 等文件。

MCU 项目还可能通过 `objcopy` 从 ELF 提取 HEX / BIN。ELF 可包含符号、段地址和调试信息；裸 BIN 主要是字节数据，本身通常不记录烧录地址。

**追问：** 为什么出现 undefined reference？检查函数是否实现、源文件是否参与构建、库链接顺序及 C/C++ 名称修饰。

### Q002：什么是交叉编译？

在一种宿主平台上，生成供另一种目标平台执行的程序。例如在 Windows / Linux PC 上使用 Arm 工具链生成 Cortex-M 固件。

除了指令集，还要匹配 ABI、浮点调用约定、目标内核、运行库和链接地址。`arm-none-eabi` 通常用于裸机 / RTOS，`aarch64-linux-gnu` 等工具链面向相应的 Linux 用户空间，不能直接混用。

### Q003：`static` 有哪些作用？

| 使用位置 | 主要作用 |
| --- | --- |
| 函数内部的局部变量 | 具有静态存储期，生命周期贯穿程序运行，名字仍只在所在作用域可见 |
| 文件作用域变量 | 具有内部链接，其他翻译单元不能通过同名 `extern` 直接引用 |
| 文件作用域函数 | 具有内部链接，用于隐藏模块内部实现 |

静态局部变量保留上次调用后的值，但并不自动具备并发安全性。C 中静态存储期对象在程序启动前完成初始化；C++ 函数局部静态对象还涉及首次执行到声明时的初始化规则。

**追问：** 其他文件如何访问模块内部状态？提供受控的 getter / setter 或模块接口。

### Q004：`volatile` 的作用是什么？

告诉编译器该对象可能以当前代码流之外的方式变化，需要按实现规定保留对它的访问。典型用途是内存映射寄存器，以及特定平台上的中断共享标志。

`volatile` 不保证复合操作原子性，不提供线程间同步，也不能代替 CPU 内存屏障或 Cache 维护。例如 `volatile_count++` 仍可能由读、加、写多个步骤组成。

**追问：** 主循环和 ISR 都修改一个计数器怎么办？根据平台使用短临界区、适合中断环境的原子操作，或改为消息传递。不能只添加 `volatile`。[参考：GCC volatile 说明](https://gcc.gnu.org/onlinedocs/gcc-8.1.0/gcc/Volatiles.html)

### Q005：`const int *p` 与 `int *const p` 有何区别？

- `const int *p`：不能通过 `p` 修改目标对象，但可以改变 `p` 的指向。
- `int *const p`：不能改变 `p` 的指向，但可通过 `p` 修改可写的目标对象。
- `const int *const p`：上述两方面都受限制。

`const` 并不等于“必定位于 Flash”。存放位置受存储期、链接脚本和优化影响。若原对象本来就定义为 `const`，强制去掉限定后写入会产生未定义行为。

### Q006：`extern` 能做什么？

用于声明定义在其他位置的对象或函数；普通函数声明通常已具有外部链接。声明使编译器知道类型，链接器仍需找到匹配的定义。

头文件中通常写 `extern int counter;`，在一个 `.c` 文件中写 `int counter;`。不要在多个 `.c` 共同包含的头文件里放普通全局变量定义。

### Q007：`#define`、`typedef`、`const` 有何区别？

| 写法 | 本质 | 主要用途 |
| --- | --- | --- |
| `#define` | 预处理记号替换 | 条件编译、简单宏、构建配置 |
| `typedef` | 类型别名 | 简化类型表达、定义接口类型 |
| `const` | 类型限定符 | 限制通过相应表达式修改对象 |

例如 `typedef int *IntPtr; IntPtr a, b;` 中两者都是指针；若使用 `#define IntPtr int *`，展开后的 `IntPtr a, b;` 只有 `a` 是指针。宏的有效范围从定义开始直到 `#undef` 或翻译单元结束，不遵循 C 块作用域。

### Q008：用宏求两个数的最小值，要注意什么？

```c
#define MIN(a, b) (((a) < (b)) ? (a) : (b))
```

给每个参数和整体表达式加括号，避免优先级改变。但 `MIN(i++, j++)` 仍可能重复求值；混合有符号、无符号类型也可能产生意外比较结果。

固定类型时优先用函数：

```c
static inline int min_int(int a, int b)
{
    return a < b ? a : b;
}
```

`inline` 不保证编译器一定展开函数。

### Q009：如何避免头文件重复包含？

使用包含保护宏：

```c
#ifndef PROJECT_SENSOR_H
#define PROJECT_SENSOR_H

int sensor_init(void);

#endif
```

也可使用工具链支持的 `#pragma once`。重复包含保护解决的是同一个翻译单元里的重复展开，不会使头文件中的普通外部变量定义自动变得安全。

### Q010：`#include <...>` 与 `#include "..."` 有何区别？

主要是头文件搜索规则不同。工具链通常让引号形式先搜索当前文件附近，再搜索配置的包含目录；尖括号形式按系统 / 配置的包含目录查找。

确切顺序由编译器及 `-I`、`-isystem` 等选项决定，区别不应概括成“哪个更快”。

### Q011：`sizeof` 与 `strlen` 有何区别？

`sizeof` 是运算符，取得对象或类型占用的字节数，结果类型为 `size_t`；`strlen` 是字符串函数，统计第一个 `\0` 之前的字符数，要求存在可访问的终止符。

```c
char text[10] = "abc";
char *p = text;
/* sizeof(text) == 10，strlen(text) == 3。
   sizeof(p) 是该平台上 char * 的大小。 */
```

不能套用“`sizeof` 永远比 `strlen` 大 1”。普通定长类型的 `sizeof` 通常可在编译期确定，但 C 的变长数组存在运行期求值情形。

### Q012：数组名和指针有什么区别？`a` 与 `&a` 呢？

数组对象保存一组连续元素；指针对象保存地址。数组表达式在很多场景会转换为首元素指针，但数组本身不是指针。

```c
int a[5] = {1, 2, 3, 4, 5};
int *p = a;
int (*whole)[5] = &a;
```

`a` 转换后的类型是 `int *`；`&a` 的类型是 `int (*)[5]`。两者指向相同起始位置，但 `a + 1` 跨过一个 `int`，`&a + 1` 跨过整个数组。函数形参 `int a[]` 会调整为指针，在函数内不能用 `sizeof(a)` 求原数组长度。

### Q013：数组指针、指针数组、函数指针分别怎么声明？

```c
int (*array_ptr)[5];      /* 指向包含 5 个 int 的数组 */
int *pointer_array[5];    /* 含有 5 个 int * 元素的数组 */
int (*operation)(int);    /* 指向接收 int、返回 int 的函数 */
int *make_value(int);     /* 返回 int * 的函数 */
```

阅读声明时先看名字与最近的括号 / 运算符结合，再向外展开。回调函数必须与约定的函数指针类型匹配。

### Q014：如何分析 `*p++`、`(*p)++`、`*++p`？

- `*p++` 等价于 `*(p++)`：取得旧指针所指的值，再推进指针。
- `(*p)++`：修改指针所指的元素，指针本身不变。
- `*++p`：先推进指针，再取得新位置上的值。

笔记例题：`int a[5] = {1,2,3,4,5}; int *p = &a[1]; p++; int m = *p++;`，结果为 `m == 3`，`p == &a[3]`。若起始地址为 `0x2000106C` 且 `sizeof(int) == 4`，最终地址为 `0x20001078`。

### Q015：回调函数是什么？

把一段处理逻辑作为函数指针注册给其他模块，由该模块在约定时机调用。例如串口接收事件、驱动完成通知、状态机动作。

回调可以同步执行，也可以延后执行，不天然等于异步。设计接口时要说明回调运行在任务还是 ISR 中、参数归谁所有、参数有效多久、是否允许阻塞和重入。

### Q016：`memcpy`、`memmove`、`strcpy` 有什么区别？

| 函数 | 复制范围 | 关键条件 |
| --- | --- | --- |
| `memcpy(dst, src, n)` | 指定的 `n` 字节 | 源和目标不能重叠，双方可访问范围足够 |
| `memmove(dst, src, n)` | 指定的 `n` 字节 | 允许源和目标重叠 |
| `strcpy(dst, src)` | 字符串及末尾 `\0` | 目标容量足够，源是有效字符串，不能重叠 |

`memcpy` 不会自动补字符串终止符。`strncpy` 在源长度达到限制时也不保证目标以 `\0` 结尾，不能把它当作通用安全替代品。

### Q017：整数位宽、符号和移位有哪些坑？

先确定目标 ABI 和类型宽度；需要固定宽度时，在实现提供的前提下使用 `<stdint.h>` 中的 `uint32_t` 等类型。普通 `char` 是否有符号由实现决定。

无符号整数运算按模回绕；有符号整数溢出是未定义行为。移位量不能为负或大于等于提升后左操作数的位宽；构造位掩码时要留意整数提升与常量类型。

**追问：** 为什么 `signed_value < unsigned_value` 可能不符合直觉？先分析通常算术转换，不能只看变量显示的十进制数。

### Q018：浮点数为什么不适合直接判断相等？

许多十进制小数无法被有限位二进制精确表示，运算还会产生舍入误差。传感器结果比较可结合业务量纲使用绝对误差与相对误差：

`|a - b| <= max(abs_tol, rel_tol * max(|a|, |b|))`

阈值应来自测量精度与算法要求。还要处理 NaN、无穷、溢出和 MCU 是否有相应精度的 FPU。固定点可以减少部分平台的开销，但要设计缩放、溢出和舍入策略。

### Q019：C++ 在嵌入式中有哪些常见追问？

- **RAII：** 通过对象生命周期管理锁、内存或设备句柄，降低遗漏清理的概率。
- **虚函数：** 支持运行期多态，通常伴随间接调用和对象布局开销，具体取决于 ABI。
- **虚析构：** 若要通过基类指针删除派生对象，基类应有合适的虚析构设计。
- **浅拷贝 / 深拷贝：** 持有资源时要明确复制与所有权，优先使用合适的值类型或资源管理类。

是否启用异常、RTTI 和动态分配，要结合工具链、资源和项目约束决定；使用 C++ 不等于必须启用全部语言设施。

### Q020：C 与 C++ 混合编译为什么常用 `extern "C"`？

用于让 C++ 按 C 语言链接约定声明相关接口，避免因 C++ 名称修饰导致符号不匹配。可在公共头文件中写：

```c
#ifdef __cplusplus
extern "C" {
#endif

int driver_init(void);

#ifdef __cplusplus
}
#endif
```

它不是“把 C++ 实现变成 C 代码”，也不允许在 C 接口里随意暴露 C++ 类等专有类型。

## 二、内存与数据布局

### Q021：程序常见的存储区域有哪些？

| 区域 | 典型内容 | MCU 项目中的常见位置 |
| --- | --- | --- |
| `.text` | 机器指令 | Flash，部分性能敏感代码可放 RAM |
| `.rodata` | 只读数据、字符串常量 | Flash 或其他只读映射区域 |
| `.data` | 需要非零初值的可写静态对象 | 运行于 RAM，初值通常保存在 Flash |
| `.bss` | 零初始化的静态对象 | RAM，启动代码负责清零 |
| 堆 | 动态分配对象 | 链接脚本或分配器管理的 RAM 区域 |
| 栈 | 调用现场、溢出到内存的局部变量等 | RAM，各任务通常有自己的栈 |

这是常见工具链布局，不是 C 标准强制的物理分区。自动局部变量也可能被放在寄存器或被优化掉。

### Q022：RO、RW、ZI 与 Flash / RAM 占用怎样对应？

在常见 Arm 工具链报告中，RO 表示只读内容，RW 表示有初值的可写内容，ZI 表示需要零初始化的内容。

粗略估算通常为：Flash 需要代码、RO 数据及 RW 初值；RAM 需要 RW、ZI，再计入堆、主栈及任务栈等保留空间。任务栈如果已从静态数组或 RTOS 堆中分配，统计时不能重复相加。压缩、对齐和特殊段也会改变镜像大小，最终应查看 map 文件及链接脚本。

### Q023：初始化为 0 的全局变量在 `.bss` 还是 `.data`？

通常放在 `.bss` / ZI，包括 `int counter;` 和 `int counter = 0;`，这样镜像不必保存一大片零。`int counter = 1;` 通常需要 `.data` 初值。

这是常见实现策略，可以被编译选项和显式段属性改变。C 保证静态存储期对象的默认零初始化语义；裸机启动代码负责落实该语义。

### Q024：堆和栈有什么区别？

栈通常按调用关系自动使用和回收；堆由分配器按请求分配，需要明确释放责任。栈空间不足会覆盖相邻数据或触发保护异常；堆可能出现分配失败、碎片、泄漏和重复释放。

不能固定说“栈在 L1、堆在 L2”，也不能套用 PC 的容量到 MCU。两者的具体位置、大小、增长方向和缓存属性均由平台与配置决定。

### Q025：野指针、悬空指针和空指针有何区别？

- 野指针常泛指没有有效目标的错误指针，例如未初始化指针。
- 悬空指针指向生命周期已经结束的对象，例如已释放的堆块或已返回函数的局部数组。
- 空指针表示未指向对象，检查后可作为状态使用，但不能解引用。

释放后把一个变量置为 `NULL`，不能同步修复其他指向同一内存的别名。应从所有权、生命周期和接口设计上避免悬空引用。

### Q026：函数可以返回局部变量的地址吗？

不能返回自动局部对象的地址供调用方在函数返回后访问，其生命周期已结束。`return buffer;` 与 `return &buffer;` 还存在类型差异，但改成前者也无法解决生命周期问题。

可选方案包括：调用方提供缓冲区与容量、返回由调用方释放的动态对象，或在合适场景使用静态对象。静态缓冲区会引入共享和重入问题。返回字符串字面量指针可以合法，但不能修改字面量，应使用 `const char *` 表达接口意图。

### Q027：使用 `malloc` / `free` 应注意什么？

检查分配失败与长度乘法溢出，明确唯一释放责任，避免越界、重复释放及释放后使用。释放时必须传递合法的分配起始指针，不能传栈地址或块内偏移指针。

`realloc` 调整非零大小失败时，原内存仍有效；用临时指针接收结果，避免丢失旧指针。C++ 的 `new/delete`、`new[]/delete[]` 与 C 的 `malloc/free` 要正确配对。

### Q028：什么是内存泄漏？如何定位？

已经不再需要的动态内存无法被释放或持续遗漏释放，导致可用资源减少。先检查所有权与失败路径，再记录分配次数、释放次数、当前和历史最低可用内存，以及最大连续空闲块。

宿主机模块可用内存分析工具；MCU 上可给分配器加统计与调用点记录，做重复连接、创建销毁和长时间运行验证。可用内存下降不一定都是泄漏，也可能是缓存增长或碎片。

### Q029：内部碎片、外部碎片和内存池是什么？

内部碎片是分配块内部未使用的空间；外部碎片是空闲空间分散，导致总量够却没有足够大的连续块。

固定大小内存池可以用空闲链表实现快速分配与回收，适合报文块、节点等固定对象。它仍可能浪费块内空间，也可能耗尽，不会自动扩容成无限内存。变长分配器的合并策略能够缓解外部碎片，但不等于彻底消除碎片。

### Q030：结构体为什么需要对齐？如何计算大小？

对齐用于满足 ABI / 指令访问要求，也可能改善访问效率。按各成员的对齐要求安排偏移，插入必要填充，再按结构体整体对齐要求补齐尾部。

例如在 `sizeof(uint32_t) == 4`、其对齐为 4，`uint16_t` 对齐为 2，且没有打包选项时：

```c
struct Example {
    uint32_t a;  /* 偏移 0 */
    uint8_t b;   /* 偏移 4 */
    uint32_t c;  /* 偏移 8，中间有 3 字节填充 */
    uint16_t d;  /* 偏移 12，尾部再补齐 */
};              /* 常见结果：16 字节 */
```

通过 `sizeof`、`_Alignof`、`offsetof` 核对具体结果。不要推断“64 位 Windows 的 long 一定是 8 字节”；位宽取决于 ABI。打包结构体也可能造成非对齐访问，不能保证任意平台都可直接读取协议字段。

### Q031：`struct` 和 `union` 的区别是什么？

`struct` 为成员提供各自的存储空间，大小包含成员、内部填充和尾部填充；`union` 的成员共享存储，大小至少能容纳最大成员，并满足整体对齐。

写入一个联合体成员会改变共享字节。跨成员读取的语义与 C / C++ 规则、类型和具体实现相关，不适合当作跨平台序列化方案。协议编码应明确字段长度、字节序和转换方式。

### Q032：大小端是什么？如何安全处理协议数据？

小端把整数低有效字节放在低地址，大端相反。网络字节序为大端；外设协议则以器件手册为准。

解析协议可逐字节组合，例如读取大端 16 位无符号数：

```c
uint16_t read_be16(const uint8_t *p)
{
    return (uint16_t)(((uint16_t)p[0] << 8) | (uint16_t)p[1]);
}
```

调用方保证至少有两个有效字节。不要简单把任意字节指针强转成 `uint16_t *`，否则可能遇到字节序、对齐和别名规则问题。

## 三、ARM / STM32 与外设

### Q033：ARM 架构是什么？所有 ARM 芯片的模式都一样吗？

Arm 定义处理器体系架构及相关内核，常见 Cortex-A 面向应用处理，Cortex-R 面向实时处理，Cortex-M 面向微控制器；具体能力仍需查看内核型号。

经典 AArch32 的 User、FIQ、IRQ、Supervisor、Abort、Undefined、System 模式不能直接套到 Cortex-M。Cortex-M 主要区分 Thread / Handler 模式，并具有相应特权和栈选择规则。AArch64 又使用异常级别等机制。

**易错点：** 没有一个适用于所有 ARM 处理器的“无状态模式”。

### Q034：常见 Cortex-M 寄存器有什么作用？

以常见的 Armv7-M 内核为例：R0—R12 用于通用数据处理，R13 为 SP，R14 为 LR，R15 为 PC；xPSR 记录程序状态，CONTROL 参与控制 Thread 模式的特权和栈选择。

MSP 常用于主栈和异常处理，PSP 常用于 RTOS 任务栈，具体由移植实现决定。CPSR / SPSR 是其他架构状态下的概念，不能直接当作 Cortex-M 状态寄存器名称。

### Q035：STM32 上电到 `main()` 的过程是什么？

以常见 Cortex-M STM32 为例：

1. 芯片按启动配置选择启动存储区域。
2. 内核从启动向量表取得初始 MSP 和复位处理函数入口。
3. 复位处理及运行库启动过程完成必要的系统初始化、`.data` 搬运、`.bss` 清零等。
4. C++ 项目还需完成相应的静态对象初始化，再进入 `main()`。

`SystemInit`、运行库入口和段初始化的具体顺序以启动文件和工具链为准。BOOT 引脚、选项字节、地址映射也因系列不同，不能把某款 STM32 的固定地址当作通用规则。

### Q036：Bootloader 如何跳转到 App？

App 需要按自己的起始地址链接。跳转前先验证镜像完整性、入口地址、栈范围和版本等，再按照平台约定停止相关外设 / DMA、处理 SysTick 与中断状态、设置向量表和必要的内核状态。

在支持 VTOR 的 Cortex-M 上配置 `SCB->VTOR`，按 App 向量表设置初始栈并转入复位入口。栈切换和最终分支通常需要谨慎设计的底层代码，不能在改了 MSP 后继续依赖旧 C 栈帧。通常应在 Thread 模式执行移交，或通过复位进入既定启动路径。

**追问：** 为什么跳转后第一次中断就跑飞？优先检查向量表、链接地址、残留中断与栈。并非所有 Cortex-M 都有同样的 VTOR 能力。

### Q037：一次中断通常怎样执行？

外设产生事件并置位标志，在外设中断使能和 NVIC 条件满足后进入异常处理。硬件按架构保存部分现场，处理程序再保存需要的软件上下文，执行服务逻辑后异常返回。

ISR 中应读取并按手册清除相应标志，保存必要数据，把耗时工作交给任务 / 主循环。不能把所有标志都按“写 0 清零”处理，有些是写 1 清除，有些要求读状态再读数据。

### Q038：抢占优先级和子优先级有什么区别？

在支持优先级分组的 Cortex-M 上，抢占优先级决定能否打断当前异常；子优先级用于同一抢占级别的挂起中断之间排序，不能使它们互相抢占。

NVIC 的优先级数值越小，紧急程度越高；有效位数由芯片实现。FreeRTOS 任务优先级则通常是数值越大越高，两者不能混淆。分组及位数应使用 CMSIS / 厂商接口核对。[参考：CMSIS NVIC](https://arm-software.github.io/CMSIS_5/Core/html/group__NVIC__gr.html)

### Q039：主循环和中断同时修改变量，如何保护？

先判断访问宽度、对齐、读改写步骤和是否可能嵌套。即使某个单次读写指令不可分割，`count++` 或“检查后再修改”也不自动安全。

可使用短临界区并正确恢复原中断屏蔽状态，或用平台支持且适合 ISR 的原子操作。只把单个中断设为数据生产者、主循环作为消费者，也能减少共享修改，但仍需确保数据发布顺序和缓冲区边界。

### Q040：推挽输出与开漏输出有什么区别？

推挽能够主动驱动高、低电平；开漏通常只主动拉低，输出高状态实际是释放引脚，依靠上拉恢复高电平，适合 I²C、线与信号等场景。

开漏并不意味着可以把任意不同电压器件直接连接。要检查引脚耐压、输入高电平阈值和掉电状态。所谓“GPIO 八种模式”常见于 STM32F1 的分类，其他系列可能将模式、输出类型和上下拉拆开配置。

### Q041：DMA 是什么？相对 CPU 搬运有什么优缺点？

DMA 控制器按配置在外设与内存或内存之间搬运数据，减少 CPU 逐个数据单元复制的负担，适合连续采样、串口和存储传输。

CPU 仍要配置 DMA、管理缓冲区并处理完成 / 错误。还需考虑可访问的内存区域、宽度、对齐、总线竞争及缓冲区生命周期。小数据使用 DMA 可能得不偿失，DMA 完成也不总等于外设线上最后一位已发完。

### Q042：Cache 与 DMA 为什么可能出现数据不一致？

在不具备相应硬件一致性的系统里，CPU 可能读取到 D-Cache 的旧数据，DMA 也可能读不到 CPU 尚未写回的修改。

典型原则是：CPU 写好待发送数据后，在 DMA 读取前做必要的 clean；DMA 写入接收区后，在 CPU 读取前做必要的 invalidate。还应按平台要求处理接收前的脏行、内存屏障、缓存行对齐及相邻数据影响。也可把 DMA 缓冲区放入合适的不可缓存区域。具体流程以芯片手册与驱动要求为准。

### Q043：Flash 和 RAM 有什么区别？

Flash 非易失，常用于程序和持久配置；SRAM 易失，常用于运行时数据与栈。Flash 擦除和编程具有粒度、时延、寿命及电压条件限制，部分芯片在操作某个 Flash bank 时还限制同 bank 的取指。

不能只说“Flash 可以反复写”。要核对擦除单位、编程单位、允许的位变化、ECC 约束和掉电行为。

### Q044：定时器、PWM 的频率如何计算？

对常见向上计数、边沿对齐的 STM32 定时器：

`f_update = f_TIM / ((PSC + 1) × (ARR + 1))`

典型 PWM 模式下，占空比可近似写为 `CCR / (ARR + 1)`，但要考虑模式、极性及边界值。中心对齐、重复计数器和外部时钟等会改变关系。

不要直接把 CPU 主频代入 `f_TIM`；先从时钟树确认 APB 分频和定时器倍频规则。说明 PSC、ARR、CNT、CCR 的用途，比只背某种单片机的寄存器名更有用。

### Q045：ADC 与 DAC 有何区别？如何提高 ADC 采样质量？

ADC 把模拟量变成数字码，DAC 反向转换。ADC 的位数表示分辨率，不能直接等同于实际测量精度；还受参考电压、噪声、线性度、源阻抗和采样时间等因素影响。

理想 N 位 ADC 的量化步长约为 `Vref / 2^N`，实际码值到电压的换算按手册规定。可从参考与供电、模拟布线、采样时间、抗混叠滤波、校准和合理平均入手改善结果。

### Q046：看门狗怎样设计才有效？

看门狗在规定时间内未被刷新时触发复位等恢复动作。独立看门狗和窗口看门狗的时钟、时序限制按芯片区分。

让关键任务定期报告进度，由监控逻辑在确认系统健康后喂狗，能够发现部分任务卡死。若在一个始终运行的定时中断里无条件喂狗，即使业务已失效也可能持续刷新。

**追问：** 如何避免不断重启却无法诊断？保留复位原因、故障摘要和启动失败次数，并设计降级路径。

### Q047：SWD 调试需要哪些信号？

核心信号为 SWDIO 和 SWCLK；实际连接还需要公共地和供调试器识别目标电平的参考连接。NRST 常用于连接 / 复位控制，SWO 是可选的跟踪输出，支持情况由芯片决定。

调试器连不上时检查供电、目标电平、引脚复用、调试频率、复位连接及读保护状态。不要在未确认后果时解除可能触发整片擦除的保护。

### Q048：如何平衡执行效率与 Flash / RAM 占用？

先测量耗时和 map 文件，再找到瓶颈。常见手段包括合理选算法、减少复制、复用缓冲区、调整任务栈、裁剪库和日志、选择合适优化等级，或在测量后用空间换时间。

必须同时观察最坏时延、可维护性与功耗。不要把所有变量改成小整数，也不要盲目内联；整数提升、对齐、代码膨胀和缓存行为可能使结果相反。

## 四、通信协议

### Q049：UART、I²C、SPI 有什么区别？

| 协议 | 同步方式 | 常见信号 | 寻址与设备选择 | 典型特点 |
| --- | --- | --- | --- | --- |
| UART | 异步 | TX、RX，另需合适的参考地 | 常见为点对点，无统一地址机制 | 无共享时钟，帧开销明确 |
| I²C | 同步 | SCL、SDA | 总线地址 | 两线共享、开漏、ACK / NACK |
| SPI | 同步 | SCLK、MOSI、MISO、CS | 通常通过片选 | 常见全双工，模式与器件格式需匹配 |

实际还有单线、三线、双线 / 四线数据等变体。最大速度和距离受器件、电气条件及布线影响，不能把常用配置当作协议极限。

### Q050：同步 / 异步通信与阻塞 / 非阻塞是同一回事吗？

不是。UART 的异步是指收发没有共享的同步时钟，通过起始位和各自时钟恢复采样位置；I²C / SPI 使用时钟来确定数据采样。

阻塞 / 非阻塞描述软件调用是否等待条件满足后再返回。UART 可用阻塞轮询，也可用中断 / DMA；SPI 同样可采用非阻塞驱动。不能根据有没有 ACK 判断同步或异步。

### Q051：波特率与比特率有什么区别？115200 能传多少有效数据？

波特率是每秒符号数，比特率是每秒比特数；一个符号可能承载多个比特。常见二进制 UART 中，两者数值通常相同。

对于 115200、8N1，一个字节包含 1 起始位、8 数据位和 1 停止位，共 10 bit，不含帧间隔与上层协议开销的理论有效载荷为 `115200 / 10 = 11520 byte/s`。

### Q052：UART 帧格式是什么？UART 与 USART 有何区别？

UART 帧通常包含起始位、数据位、可选校验位和停止位，常见设置为 8N1，数据通常低位先传。收发双方须匹配波特率、字长、校验和停止位。

USART 通常还支持同步工作方式；具体功能取决于外设实现。UART 逻辑接口不等于 RS-232 电平，连接 PC 串口或工业总线时可能需要收发器。

### Q053：串口如何保证一包 10 字节完整收发？

先区分驱动搬运完成、线路发送完成和对端业务确认。接收端按帧格式做长度累计与超时处理，不能假设一次中断或读取就收到完整一帧。

应用协议可包含帧头、长度、序号、校验和 ACK / 重试；接收区满时必须有明确策略。DMA 的完成标志通常只代表搬运完成，UART 的 TC 等标志才表示发送器完成了对应的线路发送过程。

### Q054：UART 的奇偶校验能保证数据完全正确吗？

不能。奇偶校验只能检测特定错误模式，无法覆盖所有多位错误，也不提供丢包、重复或乱序的业务保障。

可靠协议还要结合 CRC、长度、序号、超时与重传。出现错误时记录噪声、帧错误、溢出等状态；降低波特率只是可能的排查手段，不能替代对根因的确认。

### Q055：为什么 I²C 要用开漏和上拉电阻？

多个设备共享 SDA / SCL 时，开漏让任意设备都能拉低线路，而不会与另一设备主动驱动的高电平发生直接冲突。所有参与者释放后，上拉让线路恢复高电平。

这种线与关系支持仲裁和时钟拉伸。上拉过大使上升沿变慢，过小则增大低电平灌电流。电阻不是永远选 4.7 kΩ。[参考：NXP I²C 规范](https://cache.nxp.com/docs/en/user-guide/UM10204.pdf)

### Q056：I²C 的起始、停止、ACK 与 NACK 怎样表示？

SCL 为高时 SDA 下降为 START，上升为 STOP；数据位通常在 SCL 低电平时变化、高电平时保持稳定。每 8 个数据位后有第 9 个应答时钟。

接收方拉低 SDA 为 ACK，释放为 NACK。读事务中，主机接收完最后一个字节后发 NACK 可以表示正常结束，因此 NACK 不一定是故障。

### Q057：I²C 地址有几位？总线上能挂多少设备？

常见为 7 位，另有 10 位寻址。7 位地址再加读写位组成线上首字节，但传给驱动 API 的是 7 位地址还是左移后的值，取决于 API。

7 位空间共有 128 种编码，标准保留了若干地址范围，不能只扣掉 `0x00` 和 `0x7F`。实际上限还受地址冲突、总线电容、器件负载等约束，不能直接回答“可挂 128 个设备”。

### Q058：I²C 多主仲裁与时钟拉伸怎样工作？

仲裁时主机在发送同时监测 SDA；若自己释放为 1，而实际总线为 0，表明有其他主机占优，应退出相应仲裁过程。不能简化成“谁先拉低谁就一直获胜”。

时钟拉伸是设备保持 SCL 为低，延迟后续时钟；主机应等待线路实际变高，并设置合理超时。硬件控制器和外设是否支持相关模式，需要逐项确认。

### Q059：如何估算 I²C 上拉电阻？

常见开漏模式下可结合上升时间与低电平电流估算：

`Rmax ≈ tr_max / (0.8473 × Cbus)`

`Rmin ≈ (Vpullup - VOL_max) / IOL`

例如上升时间上限为 300 ns、总线电容为 100 pF 时，`Rmax` 约为 3.54 kΩ；还要确认灌电流条件给出的下限是否满足。最终应实测波形，并考虑温度、容差和所有器件的电气要求。[参考：UM10204 上拉电阻计算](https://cache.nxp.com/docs/en/user-guide/UM10204.pdf)

### Q060：硬件 I²C 与软件 I²C 如何选择？

硬件控制器负责生成时序，通常 CPU 占用更低，可配合中断或 DMA，但受外设能力、引脚复用及芯片勘误约束。

软件 I²C 用 GPIO 模拟，更方便在合适引脚实现特殊时序，但要处理开漏、拉伸、超时、调度干扰和时序验证。不能认定软件实现必然不稳定，也不能认为硬件实现一定没有故障。

### Q061：SPI 四种模式怎样区分？

| 模式 | CPOL | CPHA | 时钟空闲电平 | 采样边沿 |
| --- | --- | --- | --- | --- |
| 0 | 0 | 0 | 低 | 第一个边沿，即上升沿 |
| 1 | 0 | 1 | 低 | 第二个边沿，即下降沿 |
| 2 | 1 | 0 | 高 | 第一个边沿，即下降沿 |
| 3 | 1 | 1 | 高 | 第二个边沿，即上升沿 |

主从还要匹配位序、字长、片选时序和最高频率。CPHA 描述采样在第一个还是第二个时钟边沿，不是直接等同于固定的上升 / 下降沿。

### Q062：SPI 的一次读操作为什么也需要发送？

常见 SPI 用主机产生时钟，每个移位周期可同时发收。读取时通常先发送命令 / 地址，再发送 dummy 数据以继续提供时钟，实际格式由器件规定。

SPI 没有通用的“7 位地址 + 1 位读写”帧，也不保证一定高位先传。某些器件在命令与数据之间要求片选保持有效，不能每发一字节都随意释放 CS。

### Q063：SPI 多从机、菊花链、Dual / Quad 有什么区别？

独立片选通常让多个从机共享时钟和数据线，以不同 CS 选择设备，并确认未选中设备能正确释放 MISO。菊花链让数据经过多个器件移位，必须有器件支持。

Dual / Quad SPI 在支持的阶段使用多根数据线，并不简单等同于把所有 SPI 操作“自动加速两倍 / 四倍”。命令、地址、dummy 和数据阶段各自的线宽由协议规定。

### Q064：经典 CAN 的标准帧与扩展帧有什么区别？

标准格式使用 11 位标识符，扩展格式使用 29 位标识符。它们描述的是标识符格式；经典 CAN 的数据帧载荷均最多为 8 字节。

“扩展帧最多 64 字节”是把扩展 ID 与 CAN FD 混淆了。CAN FD 将最大数据长度扩展到 64 字节，并支持相应机制。[参考：Bosch CAN FD](https://www.bosch-semiconductors.com/products/ip-modules/can-protocols/can-fd/)

### Q065：CAN 的非破坏性仲裁如何工作？

节点发送时监听总线。显性位覆盖隐性位；节点发隐性位却读到显性位时，若处于仲裁阶段，则退出发送并转入接收，不破坏胜出报文。

在可直接比较的同格式数据帧中，数值较小的 ID 通常优先。标准 / 扩展混合或帧类型不同时，还需按整个仲裁字段比较，不能只拿 11 位与 29 位整数大小作结论。

### Q066：配置 CAN 外设需要关注什么？

确认控制器时钟、位时序、采样点、收发器和引脚，再设置正常 / 回环模式、接收过滤、发送邮箱及中断。CAN FD 还要配置数据阶段时序等参数。

回环通过只能证明部分控制器逻辑可用；板间通信还要检查收发器工作模式、两端终端匹配、线缆和参考电位。过滤器只决定本节点接收处理范围，不会替代总线上的仲裁。

### Q067：RS-232、RS-485 与 UART 是什么关系？

UART 处理异步串行帧；RS-232 / RS-485 主要定义电气接口。RS-232 常见为点对点、单端收发；RS-485 使用差分信号，常见两线半双工，也存在四线全双工应用。

RS-485 的地址、帧格式与主从规则通常由上层协议定义。距离与速率存在权衡，取决于线缆、端接和器件，不能保证固定“1.5 km 且高速”。

### Q068：RS-485 半双工发送为什么容易丢最后一个字节？

软件可能在数据刚搬入 UART 或 DMA 刚完成时就关闭 DE，但 UART 移位寄存器仍在发送。应确认线路发送完成标志，再按收发器时序切换方向。

同时检查 DE / RE 极性、回显、总线冲突、终端与偏置，以及帧间隔。接收超时与应答时限要覆盖方向切换和设备处理时间。

## 五、RTOS 与并发

### Q069：前后台程序、FreeRTOS 与 Linux 如何选择？

前后台程序适合结构简单、任务量有限的系统；RTOS 提供任务、同步与时间管理，适合 MCU 上需要组织多个并发活动的应用；Linux 提供丰富进程、网络、文件系统和驱动生态，资源需求通常更高。

实时性关心满足截止时间及最坏时延，不能直接等同于“速度快”。使用 RTOS 本身不保证硬实时；Linux 的响应能力也受内核配置、硬件和应用设计影响。

### Q070：FreeRTOS 任务有哪些常见状态？

运行、就绪、阻塞和挂起。就绪任务具备运行条件；阻塞任务等待时间或事件；挂起任务需显式恢复，不能靠普通超时自动唤醒。

在单核系统中，同一时刻只有一个任务运行；中断处理是独立的执行上下文，不是普通任务状态。

### Q071：FreeRTOS 如何调度任务？时间片一定是 1 ms 吗？

以常见单核配置为例，抢占调度时选择最高优先级的就绪任务；允许时间片时，同优先级就绪任务可在 tick 边界轮转。协作式配置则依赖任务让出、阻塞等调度点。

tick 周期取决于配置，并不固定为 1 ms。关闭同优先级时间片，不意味着永远不再切换；阻塞、让出和更高优先级任务就绪仍可能改变运行任务。[参考：FreeRTOS 调度](https://www.freertos.org/Documentation/02-Kernel/02-Kernel-features/01-Tasks-and-co-routines/04-Task-scheduling)

### Q072：为什么高优先级任务死循环会让低优先级任务饿死？

只要高优先级任务始终就绪，调度器就没有理由运行更低优先级任务。时间片主要用于同优先级就绪任务间的轮转。

应让任务等待真实事件、队列或合理周期，而不是靠忙等检查标志。`taskYIELD()` 通常不能让低优先级任务在更高优先级任务仍就绪时获得运行机会。

### Q073：`vTaskDelay` 与 `xTaskDelayUntil` 有何区别？

`vTaskDelay` 按调用时刻进行相对延时，任务自身执行时间会影响周期；`xTaskDelayUntil` 根据记录的参考唤醒时间安排周期，更适合周期任务。

它们都以 tick 为基础，不保证任意负载下严格准时。任务超期、tick 量化和更高优先级活动都要纳入设计；所用版本的具体 API 名称与返回语义以头文件为准。

### Q074：创建任务时要传哪些参数？

任务入口、名称、栈深度、参数、优先级与句柄输出等。任务函数一般包含循环，结束时应按内核规定删除任务，不能随意返回。

上游 FreeRTOS 的 `xTaskCreate` 栈深度以 `StackType_t` 元素数计，不应直接当作字节；封装或移植可能有不同约定。任务参数指向的对象必须活得足够久，还应检查创建结果。[参考：FreeRTOS 内存与任务栈](https://www.freertos.org/Why-FreeRTOS/FAQs/Memory-usage-boot-times-context)

### Q075：Cortex-M 上 SysTick、PendSV、SVC 各做什么？

在常见 FreeRTOS 移植中，tick 处理推进时间并判断是否需要切换，PendSV 用于延后执行任务上下文切换，SVC 参与启动调度等特权操作。实际系统也可用其他定时源作为内核 tick。

PendSV 通常设置为最低紧急程度，便于在较紧急的异常完成后再切换上下文。任务阻塞、主动让出和 ISR 唤醒任务等都可能请求切换，不只有 tick 一条路径。

### Q076：一次任务上下文切换保存什么？

保存当前执行状态，更新当前任务的栈位置，再恢复下一任务的状态。Cortex-M 常由硬件异常入栈保存部分寄存器，移植汇编保存剩余所需寄存器，TCB 记录栈位置等信息。

浮点上下文和栈布局取决于内核与配置。局部变量通常已经处在各自任务的栈或寄存器中，不是每次切换都把全部局部对象复制到另一个地方；任务代码通常仍从 Flash 等代码区执行。

### Q077：队列、信号量、互斥量、事件组、任务通知怎么选？

| 机制 | 适合用途 | 需要说明的边界 |
| --- | --- | --- |
| 队列 | 传递固定大小消息 | 默认复制队列项；若传指针须约定生命周期 |
| 二值 / 计数信号量 | 事件同步、资源计数 | 二值信号量会合并多次未处理事件 |
| 互斥量 | 保护共享资源 | 有持有者语义，FreeRTOS 具有优先级继承 |
| 事件组 | 多个事件条件组合 | 事件位不能直接表示任意次数的重复事件 |
| 任务通知 | 面向指定任务的轻量通知 | 需明确通知索引与使用模式，不能随意充当广播 |

### Q078：互斥量与二值信号量的关键区别是什么？

互斥量用于保护资源，具有任务持有者及释放约定；FreeRTOS 的互斥量还具备优先级继承。二值信号量常用于任务间或 ISR 到任务的事件同步，没有相同的优先级继承语义。

递归互斥量允许同一任务多次获取，必须配对释放；它不是“可以由任何任务反复拿取的计数信号量”。[参考：FreeRTOS 二值信号量](https://freertos.org/Embedded-RTOS-Binary-Semaphores.html)

### Q079：什么是优先级反转？优先级继承能解决所有问题吗？

低优先级任务持锁，高优先级任务等待该锁，而中优先级任务持续抢占持锁者，使高优先级任务被间接拖延。

优先级继承让持锁任务临时提升优先级，减少此类阻塞，但不能消除死锁、无限持锁和所有复杂嵌套依赖。仍需缩短持锁时间、固定加锁顺序，必要时采用适合系统的优先级天花板方案。

### Q080：ISR 中调用 FreeRTOS API 有哪些限制？

只使用适合该场景的 `...FromISR` 接口，不能阻塞等待；根据是否唤醒更高优先级任务，使用移植规定的方式请求切换。

在相关 Cortex-M 移植上，还要满足 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 的限制。紧急程度过高的 ISR 即使用 FromISR 接口也不能访问相应内核服务，要区分逻辑优先级与数值大小。[参考：FreeRTOS Cortex-M 中断约束](https://freertos.org/Documentation/02-Kernel/03-Supported-devices/04-Demos/ARM-Cortex/RTOS-Cortex-M3-M4)

### Q081：临界区、挂起调度器和互斥量有什么区别？

临界区通常通过端口相关的中断屏蔽机制保护短操作；挂起调度器推迟任务切换，但不会自动禁止所有中断；互斥量用于任务间资源保护，等待者可阻塞。

在单核上只禁止调度，ISR 仍可能访问同一数据；多核中只关闭本核中断也不能排除另一核访问。选择机制前先列出所有访问者和可发生的并发路径。

### Q082：FreeRTOS 的 `heap_1` 到 `heap_5` 有何区别？

| 方案 | 核心特点 |
| --- | --- |
| `heap_1` | 只分配、不回收，简单，适合对象不再释放的场景 |
| `heap_2` | 支持释放，但不合并相邻空闲块 |
| `heap_3` | 封装 C 库 `malloc/free` |
| `heap_4` | 在单个区域中管理并合并相邻空闲块 |
| `heap_5` | 支持多个非连续区域，需要提供区域配置 |

同时也可使用静态创建接口。不要把 `configTOTAL_HEAP_SIZE` 理解成所有方案都统一遵循的系统可用 RAM。[参考：FreeRTOS 内存管理](https://www.freertos.org/Documentation/02-Kernel/02-Kernel-features/09-Memory-management/01-Memory-management)

### Q083：如何评估任务栈大小、发现栈溢出？

结合最深调用链、局部大数组、库函数、浮点上下文和最坏分支估算，再在代表性压力下观察栈水位。启用溢出检查、断言或 MPU 保护，并保留异常信息。

水位是观测证据，不能保证未执行路径永远安全；哨兵法也有盲区。不要只靠“程序没崩”判断栈足够，`printf` 等函数的额外开销值得单独关注。

### Q084：空闲任务、软件定时器和 Tickless 分别做什么？

空闲任务在没有更高优先级就绪任务时运行；某些任务删除后的内存回收依赖它，因此不能长期饿死。软件定时器回调一般在定时器服务任务上下文执行，不是硬件 ISR，应避免阻塞和长耗时。

Tickless 在合适条件下减少周期 tick 唤醒以降低功耗，但需处理休眠期间的计时补偿、允许休眠长度和唤醒源。它不会让所有周期任务自动停止耗电。

### Q085：共享大缓冲区如何在多个任务间传递？

明确谁拥有、谁能写、何时移交和何时归还。可以把缓冲块指针放入队列，通过内存池管理生命周期，避免大块重复复制。

互斥量适合真正同时访问的共享对象；若按所有权单向移交，则可减少锁范围。必须处理队列满、发送失败、消费者超时和任务退出，避免块泄漏或被提前复用。

### Q086：FreeRTOS 与 RT-Thread 的知识能直接套用吗？

任务状态、同步、互斥和上下文切换等概念可类比，但具体 API、优先级方向、tick、对象生命周期及调度细节要按各内核版本确认。

面试时应说清自己用过的版本、移植平台、配置和具体模块。只背“所有 RTOS 都差不多”会遗漏实际的资源管理和实时行为差异。

## 六、Linux 与操作系统

### Q087：进程和线程有什么区别？

进程通常拥有独立虚拟地址空间；同一进程的线程共享地址空间和许多资源，但各有执行上下文与栈。Linux 调度的是任务，不能只用“进程大、线程小”解释。

线程同步方便但容易出现数据竞争，一个线程的非法操作可能破坏整个进程。进程隔离更强，但共享内存、设备和系统资源仍可能形成相互影响。

### Q088：什么是用户态和内核态？

它们区分执行权限和可访问资源。应用通过系统调用请求内核服务；内核负责驱动、内存、调度等受保护功能。

用户空间指针不能随意在驱动里直接解引用，要使用合适的用户访问接口并检查返回值。系统调用的模式切换也不一定每次都伴随切换到另一个进程。

### Q089：进程间通信有哪些方式？

管道、FIFO、消息队列、共享内存、Socket、信号及相应同步机制。按数据量、边界、是否跨机器、延迟、所有权和访问控制选择。

共享内存减少复制，但不会自动解决同步和生命周期；信号适合通知，不适合随意承载大块业务数据；Unix 域 Socket 可用于本机进程通信。

### Q090：`fork`、`exec`、僵尸进程和孤儿进程是什么？

`fork` 创建子进程，常见 Linux 实现使用写时复制；`exec` 族在成功时用新程序映像替换当前进程映像，不返回原来的执行流程。

子进程已退出而退出状态尚未被回收时形成僵尸；父进程先退出的子进程会被相应机制重新托管。父进程应使用合适的等待方式回收子进程状态。

### Q091：死锁的必要条件是什么？如何避免？

经典条件为互斥、占有并等待、不可剥夺、循环等待。固定全局加锁顺序、缩短锁范围、避免持锁等待外部操作，可减少死锁风险。

超时有助于恢复，但要设计回滚和清理路径。活锁是持续活动却不取得有效进展；饥饿是某个执行者长期得不到资源，两者与死锁不同。

### Q092：互斥锁、自旋锁和读写锁如何选择？

互斥锁适合可睡眠上下文，竞争时等待者可以睡眠；自旋锁用于很短、不能睡眠的临界区，等待时忙转；读写锁允许合适条件下的多读者并发。

不能在持有自旋锁时执行可能睡眠的操作。锁的选择还要看是否与 ISR 共享、多核行为、实时内核语义及竞争情况。读多写少也不代表读写锁一定更快。

### Q093：阻塞、非阻塞、I/O 多路复用与异步 I/O 有何区别？

阻塞调用会等待条件；非阻塞调用在暂时无法完成时尽快返回；多路复用允许一次等待多个描述符的就绪事件；异步 I/O 通常通过提交请求并接收完成结果组织工作。

“就绪”不等于整笔业务数据已经到齐，也不等于随后所有操作都绝不会阻塞。应结合 API、数据长度和并发访问设计状态机。

### Q094：`select`、`poll`、`epoll` 有什么区别？

`select` 使用描述符集合，并受集合表示及实现限制；`poll` 使用数组；`epoll` 维护注册对象和就绪事件，适合某些大量连接场景。

不能简单断言 epoll 永远是 O(1) 或永远最快。连接数量、活跃比例、事件处理成本和系统调用次数都会影响结果。

### Q095：epoll 的 LT 与 ET 应怎样使用？

LT 在条件仍满足时可持续报告就绪；ET 关注状态变化，常配合非阻塞 I/O，处理时循环读写直到 `EAGAIN`，并正确应对 EOF、错误和公平性。

如果 ET 模式只读一次就退出，可能留下未处理数据却不再收到期望的新边沿。多个工作线程共享连接时，还需明确事件所有权和并发保护。

### Q096：Linux 中断上半部和后续处理怎样划分？

硬中断处理应尽快确认来源、处理必须及时完成的硬件操作并安排后续工作。后续可使用线程化中断、工作队列等符合需求的机制。

不是所有“下半部”都允许睡眠；软中断与进程上下文的工作队列不同。Linux IRQ handler 具有规定的参数和 `irqreturn_t` 返回值，不能把裸机 ISR 的签名套过来。

## 七、网络与物联网

### Q097：TCP 与 UDP 有何区别？

TCP 提供面向连接的可靠有序字节流，没有应用报文边界；UDP 提供数据报，保留报文边界，但不保证交付、顺序和去重。

“可靠”不等于业务已经处理成功，也不代表在断网时一直能交付。选型看时延、重传策略、拥塞处理、消息边界与应用容错要求，不能只说 UDP 一定更快。

### Q098：TCP 三次握手完成什么？

常见过程为 SYN、SYN+ACK、ACK，用于建立双方连接状态、同步初始序列号并协商相关选项。

第三次确认让被动打开方确认自己的序列号已被对端接收，同时降低旧连接报文误建连接的风险。握手不是身份认证，安全身份通常需要更上层机制。

### Q099：TCP 关闭为什么常说四次挥手？TIME_WAIT 有什么用？

TCP 双向数据流可分别关闭；一方发 FIN、对端确认后，另一方向可能仍有数据待发送，所以两个方向的关闭经常分开完成，报文也可能合并。

主动关闭方通常进入 TIME_WAIT，以处理末尾确认丢失时的 FIN 重传，并让旧连接的重复报文在网络中消退。不是固定“客户端才会进入”。

### Q100：TCP 如何实现可靠传输？流量控制与拥塞控制有何区别？

序列号、确认、校验、重传及接收端重排等共同提供有序可靠字节流。流量控制保护接收端处理能力，拥塞控制根据网络状况调节发送行为。

重传、窗口和缓冲区会影响时延；把应用发送缓冲填满不代表对端已收到，更不代表业务已落盘。

### Q101：TCP “粘包 / 拆包”怎样处理？

这是应用把字节流误当成消息边界后的表现。一次 `send` 不对应一次 `recv`；数据可能被合并，也可能分次读出。

常见定界方法包括固定长度、长度字段和分隔符。解析时累计数据、检查长度上限、处理不完整头部与载荷，规定异常后的重新同步策略。长度字段不可信，不能直接拿来无限分配内存。

### Q102：Socket 收发时有哪些常见错误？

漏处理短读 / 短写、`EINTR`、非阻塞 `EAGAIN`、连接关闭和超时。对 TCP 而言，`recv` 返回 0 通常表示对端有序关闭接收方向对应的数据流；错误需结合返回值和错误码处理。

发送成功通常只说明数据被本机协议栈接受。跨连接重试业务请求时要考虑幂等性，避免对端已处理但应答丢失后重复执行。

### Q103：子网掩码、网关、ARP 和 DNS 分别做什么？

子网掩码 / 前缀描述网络范围；路由表决定下一跳，默认网关处理没有更具体路由的目的地；ARP 在 IPv4 局域网解析邻居链路层地址；DNS 解析域名等记录。

排查联网问题可按链路、地址、路由、邻居解析、域名、端口和应用协议逐层检查。能 ping 通不代表业务端口可用。

### Q104：MQTT 的基本通信流程与 QoS 有何含义？

客户端连接 Broker，按主题发布 / 订阅消息，并处理保活、重连和会话状态。QoS 0、1、2 分别提供协议层“最多一次”“至少一次”“恰好一次”的交付语义。

QoS 2 也不自动保证业务副作用恰好发生一次。断线重连、消息过期和重复消费需要应用设计；Retain、持久会话与遗嘱消息是不同机制，不能混用概念。

### Q105：如何排查嵌入式设备“网络正常但业务不通”？

记录 IP、网关、DNS、时间、远端地址和错误码；分辨域名解析失败、TCP 建连失败、TLS 握手失败、鉴权失败与应用超时。

使用抓包、服务日志和设备日志对齐时间线。TLS 场景还要核对设备时间、证书链、主机名和支持算法。不要把关闭证书校验当作正式修复。

## 八、数据结构与手写题

### Q106：数组和链表如何选择？

数组连续存储，支持常数时间下标访问，局部性通常较好；链表节点通过链接组织，定位节点通常需要遍历。

链表在已经拿到所需节点及相邻信息时可高效插删，但搜索、分配和缓存开销可能很高。不能笼统说“链表增删改查都比数组快”。

### Q107：如何实现环形缓冲区？怎样区分满和空？

下面采用“保留一个空位”的方案，`head` 为读位置，`tail` 为写位置，容量为 `RB_SIZE - 1`。代码是单执行流示例；移入 ISR / 多任务环境前需要补足适合平台的同步与内存顺序设计。

```c
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

#define RB_SIZE 8u

typedef struct {
    uint8_t data[RB_SIZE];
    size_t head;
    size_t tail;
} RingBuffer;

static bool rb_put(RingBuffer *rb, uint8_t value)
{
    size_t next = (rb->tail + 1u) % RB_SIZE;
    if (next == rb->head) {
        return false;
    }
    rb->data[rb->tail] = value;
    rb->tail = next;
    return true;
}

static bool rb_get(RingBuffer *rb, uint8_t *out)
{
    if (rb->head == rb->tail) {
        return false;
    }
    *out = rb->data[rb->head];
    rb->head = (rb->head + 1u) % RB_SIZE;
    return true;
}
```

使用前将 `head` / `tail` 初始化为 0，传入有效指针。满时可返回失败、丢新数据或覆盖旧数据，但要明确业务选择并记录溢出。

### Q108：如何反转单链表？

用 `prev`、`cur`、`next` 三个指针，先保存后继，再反转当前节点指向。遍历一次，时间 O(n)，额外空间 O(1)。

```c
typedef struct Node {
    int value;
    struct Node *next;
} Node;

Node *reverse_list(Node *cur)
{
    Node *prev = NULL;
    while (cur != NULL) {
        Node *next = cur->next;
        cur->next = prev;
        prev = cur;
        cur = next;
    }
    return prev;
}
```

需包含定义 `NULL` 的头文件。前提是链表无环且节点有效；空链表和单节点自然适用。

### Q109：如何判断链表是否有环并找到入口？

快指针一次走两步，慢指针走一步；相遇表示存在环。相遇后把一根指针放回头部，两者每次各走一步，再次相遇的位置即入口。

注意先判断快指针及其后继是否为空，覆盖自环、头部入环和无环。相遇的第一次位置通常不是入口。

### Q110：常见排序算法复杂度与稳定性如何比较？

| 算法 | 平均时间 | 最坏时间 | 典型辅助空间 | 常见实现稳定性 |
| --- | --- | --- | --- | --- |
| 插入排序 | O(n²) | O(n²) | O(1) | 稳定 |
| 冒泡排序 | O(n²) | O(n²) | O(1) | 稳定 |
| 选择排序 | O(n²) | O(n²) | O(1) | 不稳定 |
| 快速排序 | O(n log n) | O(n²) | 递归栈平均 O(log n)，最坏 O(n) | 不稳定 |
| 归并排序 | O(n log n) | O(n log n) | 常见数组实现 O(n) | 可稳定 |
| 堆排序 | O(n log n) | O(n log n) | O(1) | 不稳定 |

插入 / 冒泡的稳定性依赖对相等元素的处理；带提前结束的冒泡对有序输入可达 O(n)。MCU 选型还需考虑栈深、最坏时延和样本规模。

### Q111：如何设置、清除、翻转和测试某一位？

对 `uint32_t value`，先保证 `bit < 32`：

```c
uint32_t mask = (uint32_t)1u << bit;
value |= mask;                /* 置位 */
value &= ~mask;               /* 清位 */
value ^= mask;                /* 翻转 */
bool is_set = (value & mask) != 0u;
```

对硬件寄存器进行读改写前，要核对是否有写 1 清除、副作用或专用原子置位 / 复位寄存器，不能把普通内存示例直接套用。

### Q112：不使用第三个变量交换两个整数是否值得用？

异或交换要求两个独立且可修改的整数对象；若同一个对象被当作两者，操作可能把值清零。加减交换还可能产生有符号溢出。

面试可解释原理与限制，实际代码通常用临时变量更清楚，编译器可自行优化。表达“为何不用技巧”也是工程判断的一部分。

## 九、故障排查与项目追问

### Q113：遇到 HardFault 怎样定位？

先保留异常现场，确认是哪个栈、异常前的 PC / LR / xPSR 和有效的故障状态。对支持相关寄存器的 Cortex-M，读取 CFSR、HFSR，并按有效位判断是否使用 BFAR / MMFAR。

把故障地址与 ELF、map 和反汇编对应，检查越界、悬空指针、栈溢出、非对齐访问及非法指令。若故障发生在异常入栈或栈本身已经损坏，不能盲信栈帧内容。不同内核的故障寄存器能力不同。

### Q114：I²C 无应答或总线被拉低，怎么排查？

按电源与复位、地址格式、引脚复用、上拉与波形、事务格式、外设状态的顺序排查。区分地址 NACK、数据 NACK、时钟拉伸和真正卡死。

若 SDA 被拉低且 SCL 能控制，可按规范和器件要求尝试总线清除时钟并产生 STOP；若 SCL 一直被拉低，不能靠主机“强行输出高电平”解决，要定位拉低源并考虑设备复位 / 电源恢复。所有等待都应有超时。

### Q115：SPI 一直读到 `0xFF` 或 `0x00`，怎么排查？

先测供电、复位与 CS，再核对引脚复用、MISO 是否浮空、CPOL / CPHA、位序和速率。然后确认命令、地址长度、dummy 周期和片选保持要求。

先用低速、轮询、小数据读固定 ID 建立基线，再引入 DMA 和高频。逻辑分析仪适合检查帧与边沿关系，示波器有助于确认电平、上升沿和信号完整性。

### Q116：串口偶发丢包，怎么确认发生在哪一层？

给测试帧加序号和校验，统计 UART 错误、DMA / 接收缓冲溢出、队列满和解析失败。对齐线上抓取数据与软件计数，定位是线路错误、搬运遗漏还是业务来不及处理。

检查最长关中断时间、ISR 延迟、DMA 回卷、消费者吞吐和日志开销。只把缓冲区扩大可能暂时掩盖问题，应评估最坏积压量和持续处理能力。

### Q117：Flash 配置保存如何保证掉电后还能恢复？

使用不同擦除单元的 A / B 两份记录，包含魔数、格式版本、序号、长度、数据校验和提交状态。始终保留一份已验证的旧记录。

1. 擦除非当前有效记录所在的备用单元。
2. 写入新头部和数据，提交状态保持未完成。
3. 回读校验后，按器件编程粒度与 ECC 约束写入完成标记。
4. 启动时同时校验标记、长度和 CRC，再在有效记录中选最新序号。

不能只靠 `valid + version` 判断完整性，也不能先擦掉唯一有效副本。序号回绕、擦写寿命、标记编程原子性及各阶段断电都要测试；某些 Flash 不允许在同一编程单元上任意重复编程，应专门安排提交记录。

### Q118：系统偶发卡死，但看门狗没有复位，怎么分析？

先判断看门狗是否已启用、其时钟和调试冻结设置是否正确，以及谁在刷新。若中断无条件喂狗，任务死锁仍可能持续喂狗。

保留每个关键任务的进度与最后运行时间，结合中断计数、运行状态、锁等待链和栈水位判断是死锁、饿死、忙等还是异常。通过可控故障注入验证监控是否真正能发现业务停滞。

### Q119：低功耗模式进入后无法唤醒，应检查什么？

确认所选模式下哪些时钟、RAM 和外设仍保持，唤醒引脚 / 中断 / RTC 是否支持该模式，是否清除了旧标志并正确配置触发条件。

唤醒后还要恢复时钟、外设与通信状态。实测电流曲线并关联日志，避免调试器、串口打印和未休眠的外设改变结果。tick 补偿与实际业务时间也需统一。

### Q120：怎样把一个项目讲清楚并经得起追问？

说明需求和资源约束、系统架构、自己的职责、关键取舍，以及可复现的验证结果。至少准备一个故障闭环：现象、复现条件、证据、根因、修复和回归。

对“性能提升”“零丢包”“稳定运行”等表述给出条件、样本量和测量方式。没有做过的模块要明确界限，再说明已理解的接口和后续验证思路。

## 十、AUTOSAR 专项

### Q121：AUTOSAR Classic 与 Adaptive 分别解决什么问题？

**来源：自行延伸。**

Classic Platform 主要面向具有可预测性与实时约束的深度嵌入式 ECU；Adaptive Platform 面向高性能 ECU，以服务、进程及 POSIX 环境等机制组织应用。两者是不同平台方案，不能只看成“老版本与新版本”。

选型要考虑硬件、功能分布、实时性、升级方式及现有软件生态；不能用“车上跑 Linux 就一定是 Adaptive”来判断。[参考：AUTOSAR 平台概览](https://www.autosar.org/standards)

**延伸追问：** 同一辆车中两种平台如何交换数据？先说明接口与协议边界，再讨论网关、序列化、时序和故障处理。

### Q122：如何解释 SWC、RTE、BSW、MCAL 与 CDD？

**来源：自行延伸。**

应用由软件组件 SWC 组织；RTE 为组件通信与访问基础软件提供生成的接口；BSW 提供系统、通信、存储等基础能力。MCAL 是面向具体微控制器的抽象层；CDD 用于具有特殊需求的复杂驱动。

应用可以通过端口与接口减少对具体芯片的依赖，但 RTE 并不是独立操作系统，CDD 也不意味着可以忽略并发、时序和安全约束。[参考：AUTOSAR Classic 架构](https://www.autosar.org/standards/classic-platform/)

**延伸追问：** 更换 MCU 后哪些部分更可能变化？从 MCAL、启动链接、ECU 配置与时序验证回答，不能承诺应用完全无需验证。

### Q123：AUTOSAR OS 与 FreeRTOS / 自研 OS 有何区别？

**来源：公开面经主题，[M02 经纬恒润](https://www.nowcoder.com/feed/main/detail/d473e2d68c8b4345a340f72a3fe365ad)、[M03 元戎启行](https://www.nowcoder.com/discuss/661915293345644544)。原帖分别涉及 AUTOSAR OS 了解程度与自研 OS 的选择。**

Classic OS 基于 OSEK / VDX 体系扩展，强调配置、任务 / 事件 / 资源模型，并按扩展能力提供保护、多核等机制。FreeRTOS 提供另一套内核模型与 API，自研 OS 的能力则需要具体说明。

回答应比较配置方式、调度和事件模型、保护能力、工具链集成及验证成本，而不是笼统判断谁“更实时”。[技术参考：AUTOSAR OS R23-11](https://www.autosar.org/fileadmin/standards/R23-11/CP/AUTOSAR_CP_SWS_OS.pdf)

### Q124：Runnable 是任务吗？Basic Task 与 Extended Task 有何区别？

**来源：自行延伸。**

Runnable 是 SWC 内由 RTE 事件触发的可执行实体，通常映射到 OS 任务执行，不等于每个 Runnable 都有独立线程或独立栈。

Basic Task 不能使用 Extended Task 的事件等待机制；Extended Task 可通过事件进入等待并被唤醒。时间事件、数据接收与操作调用等触发方式，应与 Runnable 到任务的映射一起分析。

**延伸追问：** 一个 10 ms Runnable 最坏运行 15 ms 会怎样？评估激活限制、积压、截止时间和错误报告，不能只说“下次自动补跑”。

### Q125：AUTOSAR Category 1 / Category 2 ISR 如何区分？

**来源：自行延伸。**

Category 1 ISR 不受 OS 按 Category 2 的方式管理，不能随意调用 OS 服务；Category 2 ISR 通过 OS 管理入口，可在规范允许的调用级别使用相应服务。

二者的优先级、服务调用限制及保护能力要依规范和实现确认。不能把 Cortex-M 的“优先级数值大小”直接当作 ISR 类别，也不能把所有裸机 ISR 自动归为某一类。

**延伸追问：** 为什么 ISR 中不能随意等待资源？说明执行上下文、调度限制及可能形成的阻塞链。

### Q126：怎样测量 OS 栈使用量和 CPU Load，结果有什么盲区？

**来源：公开面经主题，[M02 经纬恒润](https://www.nowcoder.com/feed/main/detail/d473e2d68c8b4345a340f72a3fe365ad)。**

栈可结合预填模式、水位扫描、编译器静态分析与硬件保护测量。需要区分任务栈、ISR 栈与共享栈，覆盖最深调用链和异常路径；只运行一段时间得不到完整的理论上界。

CPU Load 可通过空闲时间或切换 / 中断钩子的计时统计估算，先定义分母与统计窗口，并说明 ISR、多核、睡眠、时钟变化和测量开销如何处理。`1 - 空闲占比` 是否符合需求，取决于这些记账规则。

**延伸追问：** 为什么平均负载 40% 仍会超期？平均值不能说明局部突发负载、最长阻塞与最坏响应时间。

### Q127：一条应用 CAN 信号通常如何穿过 AUTOSAR 通信栈？

**来源：自行延伸。**

对典型 Classic 信号通信，可概括为 `SWC → RTE → Com → PduR → CanIf → Can Driver → 控制器 / 收发器`，接收方向相反；实际项目可有网关和其他配置变体。

分别说明信号打包、PDU 路由、硬件抽象和发送确认的作用。Com 的周期 / 触发方式、控制器状态与收发器状态都可能影响最终能否发到线上。诊断通信通常涉及 CanTp，不应直接套用同一条信号路径。

**延伸追问：** `Rte_Write` 返回后能否证明整车网络已经收到？不能，要区分本地接口、缓存、发送请求、确认与远端业务处理。

### Q128：使用配置工具配置 CAN 模块，应重点检查哪些项目？

**来源：公开面经主题，[M02 经纬恒润](https://www.nowcoder.com/feed/main/detail/d473e2d68c8b4345a340f72a3fe365ad)。原帖涉及 Vector 工具中的 CAN 配置。**

从控制器 / 通道、时钟与波特率、硬件对象和句柄、ID 与过滤、PDU 映射、收发模式、通知 / 主函数配置以及网络状态管理逐层检查。

关注 Can、CanIf、PduR、Com 与相关状态管理配置是否一致，不能只改底层波特率。工具界面名称可能不同，回答应解释参数作用及其对应的数据路径。

**延伸追问：** 为什么生成代码成功却没有报文？检查初始化顺序、通信模式、周期主函数、路由与发送确认链，并抓取实际波形。

### Q129：DCM、DEM、UDS 和 DTC 分别是什么？

**来源：公开面经主题，[M02 经纬恒润](https://www.nowcoder.com/feed/main/detail/d473e2d68c8b4345a340f72a3fe365ad)。原帖涉及 UDS 服务及 `0x19 / 0x04`。**

UDS 是诊断服务协议；DCM 负责诊断通信与服务处理；DEM 管理诊断事件及故障状态等信息；DTC 是诊断故障码。应用检测到异常后报告事件，与测试仪读取诊断信息不是同一步。

`0x19` 为读取 DTC 信息服务，`0x04` 用于按 DTC 获取快照记录这一类请求；确切请求字段和行为应按采用的标准与 ECU 配置确认。不能把 DTC 状态、快照和扩展数据当成同一内容。

**延伸追问：** 去抖、确认、老化与清除故障码如何影响最终可读结果？分别讨论事件状态转换与存储策略。

### Q130：NvM 写请求返回成功，是否表示数据已持久化？

**来源：自行延伸。**

不一定。典型异步块写入要区分请求被接受、作业处理中和最终结果。还要看 RAM 块更新、队列、周期主函数、底层存储驱动及掉电时限。

在常见配置里，NvM 通过 MemIf 对接 Fee / Ea 等抽象及对应存储驱动；冗余块、CRC、默认值与掉电恢复行为需要显式配置和验证。不能把周期主函数未运行导致的作业停滞误判为 Flash 损坏。

**延伸追问：** 掉电前有多个关键块待写怎么办？设计优先级、最坏写入时间、保存预算与恢复策略，避免仅靠“关机时全部写完”。

<a id="can-advanced"></a>

## 十一、CAN / CAN FD 进阶

### Q131：CAN FD、经典 CAN 与扩展 ID 三者如何区分？

**来源：公开面经主题，[M03 元戎启行](https://www.nowcoder.com/discuss/661915293345644544)。原帖分别追问 CAN FD 与扩展格式。**

经典 CAN / CAN FD 是帧与协议能力的区分，11 位 / 29 位是标识符格式的区分。CAN FD 可使用相应标准或扩展 ID，并不能通过 ID 长度判断载荷是否允许 64 字节。

经典 CAN 载荷最多 8 字节；CAN FD 最多 64 字节，DLC 超过 8 后映射为规定的离散长度。总线兼容性还与节点是否支持 / 容忍 FD 帧有关。[参考：Bosch CAN FD](https://www.bosch-semiconductors.com/products/ip-modules/can-protocols/can-fd/)

### Q132：CAN FD 的 BRS 有什么用？数据阶段一定更快吗？

**来源：自行延伸。**

BRS 指示是否在规定位置切换到数据阶段位速率；支持 CAN FD 不代表每一帧都一定使用更快的数据速率。仲裁阶段仍须满足全网相关时序要求。

需要核对控制器、收发器、布线、数据相位位时序与延迟补偿等限制。仅在配置工具里提高数据波特率，不能证明线上的采样裕量足够。

### Q133：CAN 波特率、采样点和 SJW 怎样解释？

**来源：自行延伸。**

一个位由多个时间量子组成，常见表达为 `bitrate = f_CAN / (BRP × N_TQ)`，其中 `N_TQ` 包含同步段和各时间段。寄存器的减一编码要按控制器手册换算。

采样点决定在位内何时采样，SJW 限制重同步时允许调整的幅度。设置要兼顾传播延迟、振荡器误差、总线长度及控制器约束；两个节点名义波特率相同，也可能存在时序问题。

### Q134：Error Active、Error Passive 和 Bus-Off 是什么？

**来源：自行延伸。**

CAN 控制器利用发送 / 接收错误计数与相关规则进行故障限制。节点可能由主动错误状态进入被动错误状态；经典错误限制中发送错误计数超过规定阈值会进入 Bus-Off，停止正常参与总线发送。

恢复要同时考虑控制器机制与整车策略，包括触发原因、网络状态、重试间隔和故障报告。不要无间隔复位控制器反复恢复，否则可能持续干扰故障网络。

### Q135：只有一个正常 CAN 节点时，为什么发送可能不断重试？

**来源：自行延伸。**

正常发送通常需要其他能正确接收的节点在 ACK 槽确认。只有一个发送节点，或其他节点处于监听等不应答模式时，可能出现 ACK 错误和重传，取决于控制器模式。

ACK 表示至少一个接收节点确认了帧的相应链路接收条件，不证明目标应用已处理数据。不能由“没有 ACK”单独推出接收过滤器配置错误。

### Q136：DBC 的 Intel / Motorola、因子和偏移怎样理解？

**来源：自行延伸。**

DBC 描述报文、信号布局、单位、缩放与节点等信息。物理值通常按 `physical = raw × factor + offset` 转换，另需考虑有符号、范围、无效值和复用条件。

Intel / Motorola 涉及位布局与工具的起始位约定，不能只把整个多字节整数逆序就认为完成转换。应使用已知测试向量覆盖跨字节、有符号和边界信号。

### Q137：为什么诊断大报文需要 CanTp？它与 PduR 有何区别？

**来源：自行延伸。**

CanTp 在相应 CAN 传输协议下处理分段、重组与流控，涉及单帧、首帧、连续帧和流控帧；PduR 根据配置进行 PDU 路由，职责不同。

连续帧序号、块大小、最小间隔与各种超时都会影响大报文传输。必须按采用的标准版本、寻址方式及 CAN / CAN FD 配置解释，不能把经典 CAN 的单帧长度限制硬套到所有情形。

### Q138：怎样设计 CAN 通信验证，而不只是看“能发能收”？

**来源：自行延伸。**

覆盖正常周期、事件报文、过滤、ID / DLC、边界信号与大小端，再加入高负载、接收积压、断线、错误波特率、Bus-Off 和恢复。衡量丢失、延迟、抖动和错误状态。

对汽车通信还应按需求验证超时监测、计数器、应用 CRC / E2E 与降级行为。总线 CRC 和应用端到端保护解决的故障范围不同，不能互相替代。

## 十二、内存管理进阶

### Q139：剩余总内存足够，为什么仍可能分配失败？

**来源：自行延伸。**

分配可能需要连续区域、特定对齐、DMA 可达区或某种内存类型；空闲总量不能反映最大可用块。还可能受堆配置、元数据开销、区域隔离或任务权限影响。

Linux 用户态还要区分虚拟地址预留与实际物理页承诺，`malloc` 成功不必然代表后续大量写入不会触发资源问题；MCU 分配器则通常直接受实际 RAM 与配置区域限制。

### Q140：MMU 和 MPU 有什么区别？没有 MMU 能运行 Linux 吗？

**来源：自行延伸；“MCU 能否运行 Linux”在 [M01 大疆](https://ac.nowcoder.com/discuss/794763) 的实际技术面记录中出现。**

MMU 支持虚拟地址到物理地址映射并参与权限与属性控制；MPU 通常基于区域设置权限 / 属性，不提供相同的通用虚拟地址转换。

常规 Linux 系统依赖相应 MMU 能力；也有 no-MMU Linux 配置及其明显限制。因此要根据具体 MCU、内存和内核配置回答，不能绝对说“所有 MCU 都不能跑 Linux”。

### Q141：`kmalloc`、`vmalloc` 与分配标志怎么选？

**来源：自行延伸。**

`kmalloc` 通常提供物理连续的内存，`vmalloc` 提供虚拟连续而物理未必连续的区域；分配与释放 API 要正确对应。

`GFP_KERNEL` 可能睡眠，不能用于不允许睡眠的上下文；合适的非睡眠分配也可能失败，关键路径宜预分配。不能直接把 `vmalloc` 地址交给普通 DMA 映射，需使用适合设备的内存和 DMA 接口。[参考：Linux 内存分配指南](https://www.kernel.org/doc/html/v6.12/core-api/memory-allocation.html)

### Q142：驱动中的 CPU 虚拟地址、物理地址与 DMA 地址一样吗？

**来源：自行延伸。**

不一定。内核用 CPU 虚拟地址访问内存，设备可能经过总线地址转换或 IOMMU。应使用 DMA API 获取设备可用的 DMA 地址，并检查映射错误与设备地址能力。

区分 coherent 分配与 streaming 映射，明确 CPU / 设备所有权和同步时机。coherent 也不保证描述符字段按业务期望顺序被设备观察到，仍可能需要相应屏障。[参考：Linux DMA mapping](https://github.com/torvalds/linux/blob/master/Documentation/core-api/dma-api-howto.rst)

### Q143：DMA 满事件与 UART 空闲事件同时挂起，会不会重复提交数据？

**来源：公开面经主题，[M05 拓竹](https://www.nowcoder.com/feed/main/detail/ef23b80e5c954db2be0c1ea60106eb1b)。原帖讨论满事件、空闲事件及延迟处理中断的竞态。**

可能。两个事件不应各自把“当前整块数据”无条件提交，而应围绕唯一的已消费位置，结合 DMA 写位置、回卷计数与事件状态计算新增范围。

要考虑读取剩余计数时 DMA 继续变化、恰好回卷、多次回卷及事件合并。单次读取模 N 位置无法区分“没有新数据”和“已经整圈覆盖”，还需限制最大服务延迟或增加可靠的计数 / 缓冲机制。

**延伸追问：** 高优先级中断持续阻塞 10 字节接收时间怎么办？按速率和缓冲容量计算覆盖风险，再设计溢出检测与恢复，不能假定中断标志能记录每次事件。

### Q144：如何设计一个适合实时路径的固定块内存池？

**来源：自行延伸。**

启动时预留对齐存储，把空闲块链接起来；申请时取出，释放时归还，并根据访问上下文保护元数据。尽量避免在临界区里清零大块内存。

定义块大小、数量、耗尽策略、所有权、重复释放检查和统计。实时路径还要分析最长分配 / 释放时间及池满时的行为。验证应覆盖满池、回收、失败路径和长时间循环。

## 十三、汇编与底层机制

### Q145：Arm 32 位函数如何传参，谁负责保存寄存器？

**来源：自行延伸。**

按 AAPCS32，常见整数参数先使用 R0—R3，超出的部分按规则放栈，返回值按其类型使用相应位置。R0—R3、R12 等可被调用过程破坏；被调用者需要保持约定的保存寄存器和 SP，R9 用途由平台约定。

栈必须满足调用约定的对齐要求，公共接口要求 8 字节对齐。浮点硬 / 软 ABI、聚合类型和 64 位参数有额外规则，不能只背“前四个参数”用于所有类型。[参考：AAPCS32](https://github.com/ARM-software/abi-aa/blob/main/aapcs32/aapcs32.rst)

### Q146：`LDR`、`STR`、`BL`、`BX LR` 分别做什么？

**来源：自行延伸，基于原笔记 ARM 汇编主题。**

`LDR` / `STR` 常用于内存加载 / 存储，`BL` 分支并记录返回信息，普通函数中 `BX LR` 可用于返回。异常处理中的 LR 可能含 EXC_RETURN 等特殊值，不能完全按普通函数返回地址解释。

GNU 汇编写法 `LDR R0, =symbol` 是加载常量 / 地址的伪指令形式，与 `LDR R1, [R0]` 读取 R0 指向内存不同；具体展开由汇编器和目标决定。

### Q147：函数嵌套、中断和任务切换分别如何保存现场？

**来源：公开面经主题，[M05 拓竹](https://www.nowcoder.com/feed/main/detail/ef23b80e5c954db2be0c1ea60106eb1b)。**

函数调用按 ABI 保存需要保留的寄存器和返回状态；中断由硬件异常机制与编译器生成的入口 / 出口共同保存现场；RTOS 在此基础上保存任务切换所需状态。

对常见无扩展浮点帧的 Cortex-M 异常，基本帧包含 R0—R3、R12、LR、PC、xPSR。是否增加浮点帧、对齐填充以及使用 MSP / PSP，要结合内核与异常状态确认，不能把所有上下文切换都理解为“把整个栈复制一遍”。

### Q148：DMB、DSB、ISB 与编译器屏障有何区别？

**来源：自行延伸。**

编译器屏障约束编译器重排；DMB 用于所要求范围内的内存访问排序，DSB 还等待相应操作达到规定完成条件，ISB 用于同步后续指令执行上下文。

它们不等同于 Cache clean / invalidate，`volatile` 也不能代替这些操作。具体需要哪种屏障、作用域和位置，要依据架构与设备规范，而不是遇到问题就堆叠所有屏障。

### Q149：为什么优化后单步顺序变化、变量看不到？怎样读反汇编？

**来源：自行延伸；故障现场结合反汇编的思路与 M05 相关，不作为独立企业原题归因。**

编译器可能内联、常量折叠、消除未使用变量并改变指令安排，源代码行不再与指令一一对应。用匹配构建版本的 ELF 和反汇编，结合寄存器、地址和调用约定追踪实际数据流。

对优化后才出现的问题，检查未定义行为、竞态、生命周期、缺失的寄存器限定 / 同步和时序依赖。降低优化可帮助定位，但不等于完成修复。

### Q150：C 与汇编互调、内联汇编有哪些风险？

**来源：自行延伸。**

必须遵守调用约定、栈对齐、寄存器保存和指令集状态。内联汇编还要正确描述输入、输出、被修改寄存器及必要的内存影响，否则优化器可能基于错误假设生成代码。

不要在普通 C 函数里随意改 SP 再返回，也不要认为写了汇编就自动形成完整屏障。可以用编译器内建 / CMSIS 接口表达的操作，优先使用明确受支持的接口。

## 十四、驱动开发专项

### Q151：Linux 字符设备驱动的基本流程是什么？

**来源：公开面经主题，[M04 CVTE](https://www.nowcoder.com/feed/main/detail/e0df4313bbc14873a92afc86e9b16427)。**

确定设备接口和生命周期，分配 / 注册设备号，建立 `cdev` 与 `file_operations`，按需要建设设备模型与用户可见节点，实现打开、读写、控制和清理。也可在合适场景用 miscdevice 简化注册。

接口要定义阻塞行为、错误码、并发、权限及设备移除后的处理。设备节点存在不证明硬件已经可用；驱动还需完成硬件匹配和资源初始化。

### Q152：设备树解决什么问题？`compatible`、`reg`、`interrupts` 是什么？

**来源：自行延伸，围绕 M04 中的设备匹配与 probe 题补充。**

设备树描述硬件实例与连接关系，驱动按总线和设备模型进行匹配。`compatible` 参与匹配，`reg` 描述地址 / 资源，`interrupts` 描述中断，具体编码由父节点和 binding 规定。

设备树不是驱动业务代码。还要核对 `status`、pinctrl、时钟、复位与电源依赖，不能只保证字符串相同。[参考：Linux 设备驱动模型](https://cdn.kernel.org/doc/html/latest/driver-api/driver-model/driver.html)

### Q153：模块加载成功，但 `probe()` 没执行，怎么排查？

**来源：公开面经主题，[M04 CVTE](https://www.nowcoder.com/feed/main/detail/e0df4313bbc14873a92afc86e9b16427)。**

先确认驱动已注册、目标设备被创建、设备所在总线正确，然后看匹配表、设备树是否启用、内核实际使用的 DTB，以及是否已有其他驱动绑定。

如果 probe 已经执行但失败，则另查资源依赖、错误返回和 `-EPROBE_DEFER`；这与“入口从未执行”是不同问题。用日志和设备绑定状态分辨，不能只改 `compatible` 碰运气。[参考：Linux probe 基础设施](https://docs.kernel.org/6.6/driver-api/infrastructure.html)

### Q154：`read` / `write` / `ioctl` 与 `mmap` 如何设计？

**来源：公开面经主题，[M04 CVTE](https://www.nowcoder.com/feed/main/detail/e0df4313bbc14873a92afc86e9b16427) 涉及设备文件与 ioctl；mmap 比较为自行延伸。**

数据流可通过读写，控制命令可通过稳定的 ioctl 或合适的标准子系统接口，大块共享数据可在论证后考虑 mmap。用户输入需检查长度、范围与权限，正确处理部分复制和错误。

`copy_to_user` / `copy_from_user` 返回的是未复制字节数，不能误当成已复制长度。mmap 必须限制映射范围与访问属性，不应把整个硬件地址空间随意暴露给用户。

### Q155：Linux 硬中断函数有参数和返回值吗？

**来源：公开面经主题，[M04 CVTE](https://www.nowcoder.com/feed/main/detail/e0df4313bbc14873a92afc86e9b16427)。原帖回答中的“没有”不能沿用。**

常见 handler 形如 `irqreturn_t handler(int irq, void *dev_id)`。共享中断要检查本设备是否为来源，返回 `IRQ_NONE` 或 `IRQ_HANDLED` 等合适状态；线程化中断还涉及相应唤醒处理。

尽快完成必要硬件处理，把可延后工作交给合适上下文。不能因为裸机 ISR 常写成无参函数，就断定 Linux handler 没有参数和返回值。

### Q156：Linux I²C / SPI 设备驱动与 MCU 驱动有什么区别？

**来源：自行延伸，围绕 M04 中的 I²C 子系统题补充。**

Linux 设备驱动通常通过 I²C / SPI 子系统访问控制器，区分控制器驱动与挂在总线上的具体设备驱动，不应每个传感器都重新直接编写控制器寄存器操作。

在 probe 中获取设备、资源和配置，优先接入 IIO、input、hwmon 等适当子系统，并实现并发、电源管理和移除路径。MCU 驱动也应分层，但其调度和资源管理环境往往不同。

### Q157：MMIO 为什么要映射并使用专门访问接口？

**来源：自行延伸。**

驱动应通过平台提供的映射接口取得 I/O 地址，并使用适合体系结构与设备的读写接口，例如相关 Linux `readl/writel`，而不是把物理地址强转为普通指针直接访问。

需要区分地址空间、访问宽度、字节序、排序与寄存器副作用。普通 `memcpy`、对 packed 结构体赋值或随意读改写，都可能不符合设备要求。

### Q158：`devm_*` 能完全解决驱动资源释放吗？

**来源：自行延伸。**

托管资源能简化失败和解绑时的部分清理，但不会自动理解业务异步活动。移除或失败时，仍需按依赖关系停止新请求、停 DMA、屏蔽并同步中断、取消工作 / 定时器，再让资源释放。

若异步回调在私有数据释放后继续运行，会形成 use-after-free。系统关闭、电源管理、热拔除和已有打开文件也应分别定义生命周期行为。

### Q159：两个内核模块如何调用对方函数？

**来源：公开面经主题，[M04 CVTE](https://www.nowcoder.com/feed/main/detail/e0df4313bbc14873a92afc86e9b16427)。**

通过公开头文件声明及内核符号导出机制，在满足许可证、符号命名空间、版本与模块依赖等要求后链接使用。未导出的内部函数不能只靠 `extern` 就调用成功。

还要保证提供者的生命周期与并发约定。若系统已有标准子系统或注册回调机制，优先使用稳定的模块边界，避免互相导出大量内部实现。

### Q160：如何从零设计一个可验证的外设驱动？

**来源：自行延伸。**

先把手册中的电源 / 复位、时钟、寄存器语义、时序和错误恢复转成状态机；定义初始化、收发、超时、取消和反初始化的接口与所有权。

先用最小轮询路径验证固定寄存器与波形，再逐步加入中断、DMA、并发和电源管理。验证包含正常路径、边界、超时、设备缺失、总线错误及反复启停；保留错误计数和定位信息。

**延伸追问：** 如何证明驱动线程安全、可重入且可关闭？列出执行上下文、共享状态和每个异步活动的终止顺序，再用对应压力与故障场景验证。
